# 提案: TypeDB による将棋のルール表現と、AI の指し手の反則判定

将棋のルールを TypeDB 上に表し、**AI（LLM や将棋エンジン）が提案した指し手がルールに合っているか**を判定し、反則ならどのルールに反するかを根拠つきで返す仕組みを提案します。

## 要旨

1. **将棋のルールは、「駒の動き」というデータと、「禁じ手」という例外のルールに分けられる。** 駒ごとの動き（方向・距離）や成りの対応は表で書けるデータです。二歩・打ち歩詰め・行き所のない駒・王手放置・連続王手の千日手は、「動きとしては可能だが、してはいけない」という例外のルールです。法律の「原則と例外」（[docs/proposal/](../README.md)）と同じ構造です。
2. **盤と駒の動きは TypeDB のデータと関数で表せることを、試作で確かめた。** 盤を 81 マスとマスどうしの位置関係（どの方向に隣か）のデータで表し、飛車・角・香の利きを再帰関数で求めます。初期局面の先手の指し手が 30 通りになること、飛び駒が駒で止まること、王手と二歩の判定ができることを TypeDB 3.13 で確認しました（約 1 秒）。
3. **判定は「反則ごとの関数」の集まりとして作る。** 指し手 1 つを受け取り、反則ごとの関数がそれぞれ「この指し手はこのルールに反する」を返します。結果は「合法」か「反則の一覧（ルール ID と、規則の文言・理由）」です。指した後の局面が必要な判定（王手放置、打ち歩詰め）は、アプリケーションが仮の局面を作って評価します。
4. **AI とは「提案と判定」のループで組み合わせる。** AI が USI 形式（`7g7f`、`P*5e` など）で指し手を提案し、TypeDB が判定して、反則なら理由と合法手の例を返します。AI は理由を読んで指し直します。TypeDB はルールの審判で、手の良し悪し（強さ）は扱いません。
5. **正しさは、既存の将棋ライブラリとの突き合わせで確かめる。** 全合法手の数（perft）と、反則の判定結果を、広く使われている将棋ライブラリと比べます。将棋のルールは明確なので、法律の提案と違って専門家のレビューがなくても、機械的に正しさを確かめやすい分野です。

## 法律の提案との関係

| 観点 | 法律（民法） | 将棋 |
|------|-----------|------|
| ルールの構造 | 要件 → 効果、原則と例外（請求原因・抗弁・再抗弁） | 駒の動き（原則）と禁じ手（例外） |
| 判定の対象 | 事案（事実と証明状態） | 局面と指し手 |
| 根拠 | 条文・判例 | 日本将棋連盟の対局規定など |
| 正しさの確認 | 専門家のレビューが必要（確保できていない） | 既存のライブラリと機械的に比べられる |
| 推論の特徴 | 層化否定（証明できなければ不成立） | 再帰（飛び駒の利き）、仮の局面での評価、否定（「逃げる手がない」） |

将棋は、ルールが明確で正解が機械的に得られるので、**「AI の出力をルールで検査する」仕組みの検証台**として適しています。ここで作る仕組み（反則ごとの関数、根拠つきの判定結果、提案と判定のループ）は、法律や業務ルールの判定にも使えます。

## 用語

| 用語 | 意味 |
|------|------|
| 局面 | 盤上の駒の配置、両者の持ち駒、手番の組 |
| 疑似合法手 | 駒の動きとしては可能な手（王手放置などの禁じ手をまだ除いていない手） |
| 合法手 | 疑似合法手のうち、禁じ手に当たらない手 |
| 反則 | ルールに反する指し手。公式戦では反則をした側の負け |
| USI | 将棋エンジンとの通信の標準的な形式。指し手を `7g7f`（7七→7六）のように書く |
| SFEN | 局面を 1 行の文字列で表す形式 |
| perft | ある局面から N 手先までの合法手の数を数えたもの。手の生成が正しいかの検査に使う |
