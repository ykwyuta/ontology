## 7.3 設計からの変更点

| 設計（[03](03-design.md)） | 実装 | 理由 |
|------------------------|------|------|
| 王手放置は、指した後の局面を書き込んで判定 | **仮想の盤**で判定（`occupied_after`、`attacked_after`、`leaves_check`）。局面を書き込まない | 全合法手を求めるときに候補手ごとに局面を書き込むと遅すぎる。3.5 でフェーズ3に試すとしていた方法を先に採用した |
| 打ち歩詰めは、後の局面を書き込んで判定 | 設計どおり。歩を打って王手になる手だけ、後の局面を書き込んで相手の合法手の有無を調べる | 2 手先の仮想の盤は関数が複雑になる。対象の手が少ないので影響は小さい |
| 判定する指し手を `proposed-move` として書き込む | 反則の関数は、局面・マス・駒を**引数**で受け取る | 判定のたびの書き込みを減らす。評価の記録は 6.2 の評価層で別に持つ予定 |
| 指し手の判定は反則の関数で行う | まず全合法手の一覧にあるかで判定し、ない場合だけ反則の関数で理由を特定する（[06](06-decisions.md#62-設計への反映) の 2 段階） | 速さと、判定の正しさ（合法手の生成は基準と突き合わせ済み） |
| 対局と棋譜は TypeDB に持つ | 現在は Python のメモリ上で持ち、`record()` で JSON に出力 | 千日手の判定は履歴の手順の処理で、ルールの判断ではない。評価層と合わせて TypeDB に移す |

### 仮想の盤

指し手（移動元 $f → 移動先 $t）を指した後の盤を、局面を書き込まずに関数で表します。

```typeql
# 指した後に $q に駒があるか: 移動先には駒がある。移動元は空く。それ以外は元の局面のまま
fun occupied_after($p: position, $q: square, $f: square, $t: square) -> { square }:
match
  { $q is $t; } or
  { let $x in occupied_except($p, $q, $f); };
return { $q };
```

王手放置の判定（`attacked_after`）は、玉のマスから各方向に**逆向き**にたどり、最初にぶつかった駒が、その向きに利く相手の駒かどうかを調べます。相手の全駒の利きを求めるより少ない計算で済みます。持ち駒を打つ手は、移動元 = 移動先として同じ関数で扱います。

## 7.4 ルール ID ごとのテスト

[tests/shogi_tests/test_referee.py](../../../tests/shogi_tests/test_referee.py) は、各テストの期待（合法か反則か）を基準のライブラリでも確かめてから、TypeDB の判定と比べます。

| ルール | テストした局面の例 |
|-------|----------------|
| R-MOVE / R-NO-PIECE / R-TURN / R-OWN | 初期局面での誤った移動 |
| R-PROMO-ZONE / R-PROMO-PIECE / R-PROMO-MANDATORY | 敵陣外での成り、金の成り、最奥の段への歩の不成 |
| R-DROP-HAND / R-DROP-EMPTY / R-DEADEND-DROP | 持っていない駒、駒のあるマス、最奥の段の歩・奥 2 段の桂 |
| R-NIFU | 二歩。と金のある筋への歩打ちは合法 |
| R-SELF-CHECK | ピンされた金を筋の外に動かす、玉が飛車の利きに入る |
| R-UCHIFUZUME | 打ち歩詰め。逃げ道がある歩打ちの王手は合法。盤上の歩を成って詰ませる手は合法 |
| R-FORMAT | 解析できない指し手 |

## 7.5 TypeDB 3.13 で分かったこと（3.8 の続き）

| 事項 | 内容 | 対応 |
|------|------|------|
| 束縛済みの変数に `let … in` で受け直す | 引数や、先に束縛した変数を `let $t in f(...)` で受けると REP21 | 新しい変数で受けて `$u is $t;` で比べる |
| 戻り値が複数の関数 | `-> { square, square, piece-type }` のように、概念を複数返す関数は問題なく使える | 盤上の移動は（移動元・移動先・駒）の組で返す |
| 値を返す関数の `or` | 3.8 のとおり使えない | 成る手・成らない手を別の関数（`legal_moves_promoted` / `legal_moves_unpromoted`）に分ける |

テストのフォルダ名を `tests/shogi` にすると、基準のライブラリのパッケージ名（`shogi`）を隠してしまう、という Python 側の問題もありました（`tests/shogi_tests` に変更）。

## 7.6 性能

| 処理 | 時間（Windows 11、Docker Desktop、TypeDB CE 3.13.6） |
|------|---------------------------------------------|
| データベースの作成（スキーマ・盤・ルール） | 約 1.6 秒 |
| 初期局面の全合法手（30 手） | 約 1.8 秒 |
| ランダムな局面の全合法手 | 1 局面あたり平均 約 4〜8 秒（王手・持ち駒が多いほど長い） |
| perft(2)（30 局面の全合法手、計 900 手） | 約 96 秒 |

対局の審判では、1 手ごとに「判定」と「次の局面の全合法手（詰みの判定）」を求めるので、1 手あたり数秒かかります。AI 対局の審判としては使えますが、[06](06-decisions.md) の目安（数秒以内）の上限に近く、評価で大量の局面を扱うには遅い状態です。改善の候補:

- 持ち駒を打つ手の候補（空きマス × 持ち駒の種類）の王手放置の判定を、王手がかかっていないときは省く（打つ手で自玉に王手がかかることはない）
- 局面の書き込み（IID による照合）をまとめる
- 評価では、局面ごとの全合法手を一度だけ求めて保存し、使い回す
