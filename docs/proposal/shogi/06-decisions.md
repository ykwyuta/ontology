## 6.1 2 つの用途が求めるもの

| 観点 | AI 対局の審判 | LLM のルール理解の評価 |
|------|------------|---------------------|
| 何を判定するか | 対局中の 1 手ごとの合法性と、対局の終了（詰み・千日手・反則） | 用意した局面に対する LLM の指し手の合法性 |
| 誤りの影響 | 合法手を反則と判定すると、正しい手が指せず対局が壊れる | 判定の誤りが、そのまま評価結果の誤りになる |
| 反則の扱い | 公式ルールどおりなら反則負け | 反則の種類を記録し、指し直しも観察する |
| 必要な速さ | 1 手ごとに待たせない（目安: 数秒以内） | 大量の局面を一括で評価（バッチ） |
| 記録 | 棋譜と判定の結果 | 局面・プロンプト・モデル・指し手・判定・指し直しの全履歴 |
| 理由の説明 | 反則負けの根拠を残す | 反則の種類ごとの集計のキー（ルール ID）として使う |

どちらの用途も、**判定が正しいこと**が最も重要です。学習支援で重視する「初心者向けのわかりやすい説明」は優先度を下げ、ルール ID と機械的に作る理由の文で十分とします。

## 6.2 設計への反映

### 局面ごとに全合法手を求めておく

審判は、指し手の判定のほかに、**対局の終了**（指す側に合法手がない＝詰み）を判定する必要があります。そこで、局面ごとに全合法手を一度だけ求めて記録し、指し手の判定は次の 2 段階にします。

1. 指し手が全合法手の中にあるか（あれば合法。速い）
2. なければ、反則ごとの関数（[3.5](03-design.md#35-指し手の判定の流れ)）で、どのルールに反するかを特定する（理由の説明と集計のため）

全合法手を求めることは、打ち歩詰めの判定（相手に合法手がないか）、詰みの判定、評価用の「合法手の例」にもそのまま使えます。

### 判定の 2 つのモード

| モード | 用途 | 反則のとき |
|-------|------|----------|
| strict（審判） | AI 対局 | 反則負けとして対局を終える。反則の内容を棋譜に記録 |
| retry（評価） | LLM の評価、練習対局 | 反則の内容を返し、上限回数まで指し直させる。すべての試行を記録 |

### 対局の終了の判定

審判として、指し手の合法性に加えて次を判定します。

| 終了 | 判定 | 結果 |
|------|------|------|
| 詰み | 手番の側に合法手がない | 手番の側の負け |
| 反則 | strict モードで反則の指し手 | 反則した側の負け |
| 連続王手の千日手 | 同一局面 4 回、かつ一方の手がすべて王手 | 王手をかけていた側の負け |
| 千日手 | 同一局面 4 回 | 引き分け（指し直しは対局の運営に任せる） |
| 最大手数 | 設定した手数に達した | 引き分け（AI 同士の対局で一般的な打ち切り。手数は設定） |
| 投了 | AI が投了を宣言 | 宣言した側の負け |

入玉宣言法（持将棋）は、AI 同士の対局では入玉の局面が起きうるため、フェーズ3以降で検討します（それまでは最大手数で打ち切り）。

### 新しいルール ID

| ID | 内容 | 理由 |
|----|------|------|
| R-FORMAT | 指し手の書式が解析できない | LLM は書式を誤ることがある。評価の集計で区別したい |
| R-NO-PIECE | 移動元に駒がない | LLM の盤面の取り違えで多いと見込まれる。R-MOVE と区別して集計する |

### 評価のための記録

LLM の評価では、1 回の試行ごとに次を記録します（TypeDB の事案層に相当する「評価層」として持つ）。

| 記録 | 内容 |
|------|------|
| 局面 | SFEN、局面の分類（序盤・中盤・終盤、王手がかかっている、持ち駒がある、打ち歩詰めになりうる、など） |
| 入力 | プロンプトの版、局面の渡し方（SFEN のみ / 盤面図つき） |
| モデル | モデル名・版、温度などの設定 |
| 出力 | 指し手の文字列、判定（合法 / 反則のルール ID の一覧） |
| 指し直し | 何回目の試行か、前回の判定結果を渡したか |

集計の例:

| 指標 | 意味 |
|------|------|
| 1 回目の合法率 | 最初の提案が合法だった割合 |
| 反則の種類別の率 | R-NIFU、R-UCHIFUZUME、R-SELF-CHECK、R-NO-PIECE などのルール ID ごと |
| 指し直しによる回復率 | 反則の理由を返したあと、合法手を指せた割合 |
| 局面の分類別の合法率 | どんな局面で誤りやすいか |

### 評価用の局面集

ルールの理解を測るには、反則が起きやすい局面を意図的に含める必要があります。

| 分類 | 例 |
|------|-----|
| 二歩の誘惑 | 持ち駒に歩があり、歩のない筋が少ない |
| 打ち歩詰めの可能性 | 歩を打てば詰む局面（突き歩詰めは可能な局面も含める） |
| ピン | 動かすと自玉に王手がかかる駒がある |
| 王手への対応 | 王手がかかっていて、応じる手が限られる |
| 行き所のない駒 | 敵陣の奥に歩・香・桂を進める・打つ候補がある |
| 成りの判断 | 敵陣への出入りで成り・不成が選べる、行き所がなくなる |
| 通常の局面 | 公開の棋譜から無作為に選んだ局面 |

局面ごとに、全合法手と、各ルールに反する指し手の例を、基準のライブラリで作って正解として持ちます。

## 6.4 残りの論点の推奨案

まだ決まっていない論点について、2 つの用途を前提にした推奨案です。

| 論点 | 推奨 | 理由 |
|------|------|------|
| ルールの範囲 | 日本将棋連盟の公式ルール（反則負け）を既定。千日手・連続王手の千日手・詰みを含める。入玉宣言法は後回しにし、最大手数で打ち切る | 審判として必要な終了条件をそろえる。入玉宣言は点数計算が必要で後回しにできる |
| AI の入出力 | 指し手は USI。局面は SFEN に加え、LLM には盤面図（文字の図）も渡す。渡し方の違いも評価の条件として記録する | USI は機械的に解析でき、エンジンとも共通。盤面の渡し方で LLM の誤りが変わる可能性があり、それ自体が評価の対象になる |
| 検証の基準 | Python の将棋ライブラリ（python-shogi、cshogi などから、ライセンスを確認して 1 つ選ぶ）をテストと正解データの作成にだけ使う | 実行時には依存しない。正解データの作成と突き合わせに使う |
| リポジトリの構成 | 同じリポジトリに別のパッケージ（`src/shogi_referee`）として置く。判定結果の形式、MCP ツールの部品は法律と共通化を検討する | TypeDB の環境・テストの仕組みを共有できる |
