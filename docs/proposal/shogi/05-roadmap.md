# 5. 進め方・検証・リスク

## 5.1 段階的な進め方

| フェーズ | 目標 | 主な成果物 | 完了条件 |
|---------|------|-----------|---------|
| 0. 試作（済） | 盤と駒の動きを TypeDB で表せるか確かめる | [prototype/schema.tql](prototype/schema.tql)、検証スクリプト | 初期局面の指し手 30 通り、飛び駒の利き、王手、二歩を正しく判定（達成） |
| 1. ルール層と疑似合法手（**完了**: [07](07-implementation-results.md)） | 全駒・成り・持ち駒を扱う | スキーマ、ルールのデータ（ルール ID・説明・出典）、SFEN の読み込み、`board_moves`・`drop_moves`・成りの展開 | 任意の局面で、疑似合法手がライブラリと一致する |
| 2. 反則の判定（**完了**。perft(3) は未実施） | 1 手と局面で決まる反則と、王手放置・打ち歩詰め | 反則ごとの関数（`v_`）、指し手の解析（USI）、仮の局面による判定、判定結果の JSON | 全合法手（perft 1〜3）がライブラリと一致し、反則の判定がテスト用の局面でライブラリと一致する |
| 3. 履歴と性能（**一部完了**: 対局の終了と strict / retry。性能は未達） | 千日手・連続王手の千日手、判定の速さ | 対局と棋譜、SFEN による同一局面の判定、`occupancy_after` による仮の局面なしの判定の比較 | 公開の棋譜を再生して反則なしと判定でき、1 手の判定が目標時間（例: 1 秒）以内 |
| 4. AI との組み合わせ | 提案と判定のループ | MCP ツール（`validate_move` など）、LLM との対局の実験、反則率の集計 | LLM に対局させ、反則をすべて止め、理由を返して指し直させられる |
| 5. 展開 | 変種と他分野 | 将棋の変種（盤の大きさ・駒の違い）のルールデータ、法律の規範判定との共通部品の整理 | 変種をデータの追加だけで扱える |

## 5.2 検証方法

1. **単体テスト（局面テスト）**: ルールごとに、反則になる局面と指し手・ならない局面と指し手を作り、期待する判定をテストにします。とくに境界の例を用意します。
   - 二歩: と金がある筋への歩打ちは反則ではない
   - 打ち歩詰め: 歩打ちの王手でも、玉が逃げられる・歩を取れる・合駒できるなら反則ではない。歩を盤上で進めた詰み（突き歩詰め）は反則ではない
   - 成り: 敵陣から出る手でも成れる。行き所のない駒は成らなければならない
   - 王手放置: 王手をかけられているのに別の手を指す、ピンされた駒を動かす
2. **perft（全合法手の数）**: 局面から N 手先までの合法手の数を数え、広く使われている将棋ライブラリ（Python の将棋ライブラリなど）の値と比べます。初期局面の 1 手目は 30 で、試作の疑似合法手の数と一致しています。手の生成の誤りは、perft の不一致として機械的に見つかります。
3. **ランダムな局面での突き合わせ**: ライブラリで対局をランダムに進めて多数の局面を作り、各局面の全合法手と、ランダムに作った非合法手の判定を、TypeDB とライブラリで比べます。
4. **公開の棋譜**: プロ棋戦などの公開されている棋譜を再生し、すべての手が合法と判定されることを確かめます。
5. **ルールの出典**: ルールごとに、日本将棋連盟の対局規定などの出典を記録し、説明の文言と照合します。

法律の提案と違い、将棋はルールが明確で、**正解をライブラリから機械的に得られる**ので、専門家のレビューがなくても判定の正しさを高い水準で確かめられます。

## 5.3 リスクと対策

| リスク | 内容 | 対策 |
|-------|------|------|
| 性能 | 合法手の生成・打ち歩詰めの判定は、専用のライブラリより大幅に遅い | 用途を「AI の指し手 1 つの判定」に絞る（探索には使わない）。重い判定は歩打ちの王手のときだけ。フェーズ3で `occupancy_after` と比べる |
| TypeDB の制約 | 値を返す関数の `or`、属性と値の変換などで、書き方が制限される | 試作で回避策を確認済み（[03](03-design.md#38-試作で確かめたこと)）。判定関数は生成ではなく手書きだが、パターンを決めて統一する |
| 判定の誤り | 合法手を反則と判定すると、AI が指せなくなる | perft とランダム局面の突き合わせを通るまで、実際の対局には使わない |
| 仮の局面の後始末 | 判定のために書き込んだ局面が残る | 判定ごとにトランザクションを分け、最後に削除する。または読み取り専用の判定（`occupancy_after`）に移行 |
| ルールの解釈の違い | 千日手の数え方や、公式ルールと一般的なルールの違い | ルールに出典を付け、公式（日本将棋連盟）のルールを既定にする。違いは設定で切り替える |
| LLM の局面の取り違え | AI が局面を誤認し、意図と違う手を出す | 判定結果に局面（SFEN）を添え、AI に盤面図とともに渡す |

## 5.4 まず決めること

> 1（用途）は決定済み: AI 対局の審判と LLM のルール理解の評価。設計への反映、ロードマップの変更、残りの論点の推奨案は [06](06-decisions.md) にあります。

1. **用途**: AI 対局の審判、LLM のルール理解の評価、学習支援のどれを優先するか。説明の詳しさと、求められる速さが変わります。
2. **ルールの範囲**: 公式戦のルール（反則負け）を既定とするか。持将棋・入玉宣言を含めるか。
3. **AI の入出力**: 指し手を USI で受け取るか、日本語の棋譜で受け取るか。局面を SFEN で渡すか、盤面図も添えるか。
4. **検証の基準にするライブラリ**: perft と判定の突き合わせに使うライブラリを決める（ライセンスの確認を含む）。
5. **リポジトリの構成**: 法律の実装（`src/legal_onto`）と同じリポジトリに置くか、共通部品（判定結果の形式、MCP ツール）を切り出すか。
