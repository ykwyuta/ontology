# 6. 決定事項と設計への反映

[5.4](05-roadmap.md#54-まず決めること) で挙げた着手前の方針は、次のとおり決まりました（2026-10-02）。

| # | 論点 | 決定 |
|---|------|------|
| 1 | 用途 | **実務家の支援用** |
| 2 | 対象分野 | 提案どおり、**民法の意思表示（93〜98条の2）・売買（555条以下）・消滅時効（144条以下）** から始める |
| 3 | 実行環境 | **TypeDB 3.x Community Edition を docker compose でローカルに構築**し、アプリケーション（取り込み・コンパイラ・実体化パス）は **Python** で書く |
| 4 | 規範作成の体制 | 規範層をレビューする**法律の専門家は確保できない** |

## 6.1 決定どうしの緊張関係

1 と 4 の組み合わせが、このプロジェクトの最大のリスクです。実務で使う以上、規範層の誤り（要件の立て方・証明責任の配分・見解の帰属）は利用者の判断を誤らせます。一方で、その誤りを事前に見つける専門家のレビューがありません。

そこで、**「専門家のレビュー済み」という前提でシステムを作らない**ことにします。代わりに、規範の確からしさを根拠つきで記録し、それを出力のたびに利用者（実務家）に見せることで、レビューを**利用時に、利用者自身が行う**形に移します。

## 6.2 専門家レビューの代替策

| 代替策 | 内容 | 位置づけ |
|-------|------|---------|
| 典拠の明記 | 規範ごとに、要件と証明責任の配分の典拠（公刊された要件事実の教材・注釈書、条文、判例）を記録する。典拠のない規範は登録しない | 必須。規範登録の条件 |
| PROLEG との突き合わせ | PROLEG の規則ベースが対象範囲を覆っている部分は、規範と結論を突き合わせる（[5.2](05-roadmap.md#52-検証方法) の 2） | 強い検証。意味論と規範内容の両方を確かめられる |
| 教材の設例による回帰テスト | 要件事実の教材の設例と、その解説にある結論を事案テストにする | 強い検証 |
| COLIEE データ | 対象範囲の短答問題で正答率を測る | 網羅性の目安 |
| LLM による相互チェック | 規範と条文・典拠の記述の食い違いを LLM に指摘させる | 弱い検証。指摘の候補を出すだけで、採否は記録した典拠で決める |
| 利用者によるレビュー | 実務家が出力を確認する過程で規範を「確認済」「疑義あり」と記録できるようにする | 運用で積み上がるレビュー |

対象分野（意思表示・売買・消滅時効）は、要件事実の教材で扱いが確立した分野です。典拠を付けやすいので、この方針と相性がよいといえます。

## 6.3 スキーマへの反映

規範層（[4.2](04-schema-design.md#42-規範層)）に、典拠とレビュー状態を加えます。フェーズ2で実装します。

```typeql
define
  attribute review-status, value string
    @values("unreviewed", "source-checked", "proleg-matched", "user-confirmed", "disputed");
  attribute authority-ref, value string;     # 典拠 例: 書名・版・頁、判例の事件番号
  attribute review-note, value string;

  entity norm, owns review-status, owns authority-ref, owns review-note;
```

- `unreviewed`: 登録直後
- `source-checked`: 典拠と照合済み
- `proleg-matched`: PROLEG と結論が一致
- `user-confirmed`: 実務家が利用時に確認
- `disputed`: 利用者が疑義を記録した。解消するまで、その規範を使った結論には警告を出す

## 6.4 出力の約束（実務家向け）

判断クエリの結果は、結論だけでは返しません。アプリケーション層で、少なくとも次の情報を必ず添えます。

1. 結論と、その導出に使った規範・根拠条文・判例（導出記録）
2. 前提にした事実の証明状態と、採用した見解・時点
3. 導出に使った規範のうち `review-status` が `unreviewed` または `disputed` のもの
4. 評価を人が入力した規範的要件（「重大な過失」など）の一覧
5. 「システムの出力は論点の整理と立証計画の補助であり、法的判断は利用者が行う」旨の表示

位置づけは「結論を出す道具」ではなく「**論点・不足事実・根拠を漏れなく並べる道具**」とします。[5.3](05-roadmap.md#53-リスクと対策) の「法的な責任」のとおり、利用者は弁護士などの専門家、または組織内で自らの業務に使う法務担当者を想定し、一般の人への個別の法的判断の提供はしません。

### 実機検証の結果（フェーズ1の一部を前倒し）

[04](04-schema-design.md) の TypeQL を TypeDB CE 3.13.6 で検証しました。

- 4.1〜4.4 の `define` ブロックは、1 つのスキーマトランザクションにまとめれば、すべて定義できる。節をまたいで相互に参照しているので、ブロックごとに順に定義すると失敗する。省略している `defence_payment` と `defence_prescription` には、検証スクリプトでスタブを補う
- 4.2 の規範データの `insert`、4.5 の Q1〜Q4、4.6 の実体化パスは、すべて構文と型の検査を通る
- 4.5 の例題事案を投入すると、期待どおりの結果が得られる
  - 95条3項1号の事実が「真偽不明」のとき: Q1 で請求が認められ、Q2 でこの事実（立証責任は被告側）が不足事実として出る
  - 同じ事実が「証明済」のとき: 再々抗弁が成立して錯誤取消の抗弁が生き、請求は認められない

つまり、層化否定による「請求原因 → 抗弁 → 再抗弁 → 再々抗弁」の評価は、TypeDB 3.x の関数で意図どおりに動きます。
