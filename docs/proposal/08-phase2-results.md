## 8.2 提案からの変更点

### 規範の正本は YAML ファイル

提案では「規範の唯一の正本は TypeDB の規範層」としていましたが、正本は [norms/*.yaml](../../norms/) に置き、TypeDB はそれを検証して読み込んだ写しとしました。

- 専門家のレビューがないため（[06](06-decisions.md)）、規範の変更を差分で確認でき、履歴が残る形にしました。利用者が規範を確認・修正するときも、ファイルの差分として見られます。
- `legal-onto load-norms` が、検証 → 規範層への書き込み → 関数の生成と定義を一度に行います。評価のときは、DB の関数が YAML と対応しているかを確かめ、対応していなければ再読み込みを促します。

### 事案は訴訟物ごとに表す

提案 4.3 では、事案を売買契約・意思表示・当事者のグラフで表し、関数ごとに対象の型（`sales-contract`、`declaration-of-intent`）を変えていました。実装では、**推論の単位を訴訟物（`claim`）に統一**し、要件事実の認定（`fact-finding`）と時点（`time-point`）はすべて訴訟物に結びつけました（[schema/03-cases.tql](../../schema/03-cases.tql)）。

- 要件事実論は訴訟物ごとに請求原因・抗弁・再抗弁を組み立てるので、この単位が自然です。
- すべての関数が同じ形（訴訟物を受けて訴訟物を返す）になり、規範から機械的に生成できます。規範ごとに「表意者 = 買主」のような役割の対応を書く必要がなくなりました（提案 4.7 の「主体の対応」）。
- 代わりに、要件事実の説明は「請求する側」「請求される側」を主語にして書いています。同じ訴訟物の中で、意思表示が複数あるような事案は区別できません。必要になれば訴訟物を分けて入力します。

### 関数は訴訟物を引数にとる

提案 4.4 の関数は引数をとらない形（`fun mistake_rebuttal() -> { declaration-of-intent }`）でした。この形だと、否定 `not { let $c in h_x(); }` の中で呼ぶたびに全訴訟物について評価し直し、44 件の訴訟物の評価に 8 分半かかりました。訴訟物を引数にとる形（`fun h_x($c: claim) -> { claim }`）に変えて 19 秒になりました（8.8 節も参照）。

## 8.3 規範の書き方

書式は [norms/README.md](../../norms/README.md) にあります。例（錯誤取消しの抗弁）:

```yaml
- id: D95
  label: 錯誤による取消し
  effect: cancellation-by-mistake
  category: impeding
  exception-of: [G555-price, G555-delivery]
  sources:
    - path: a95/p1
      quote: 取り消すことができる
    - path: a123/p1
      quote: 相手方に対する意思表示によってする
  authority:
    - 民法95条1項・121条・123条
  when:
    all:
      - norm: NR95                        # 錯誤による取消権の発生（95条1項・2項）
      - fact: N123.cancellation-declared
        label: 請求される側が、請求する側に対し、契約の意思表示を取り消す旨の意思表示をしたこと
```

### 読み込み時の検証

| 検証 | 内容 |
|------|------|
| 書式 | 必須項目、値の範囲、参照先の規範の存在 |
| 典拠 | `authority` のない規範は登録しない（[06](06-decisions.md#62-専門家レビューの代替策)） |
| 層化 | 例外関係と規範の参照に循環がないこと |
| 証明責任 | 層（請求原因 0、抗弁 1、…）を例外関係から計算し、偶奇が一意に決まること。偶数なら請求する側、奇数なら請求される側が証明責任を負う |
| 要件事実の一貫性 | 同じ `fact-code` の説明と規範的要件かどうかが、規範の間で一致すること |
| 根拠条文 | 条文層に規定があり、`valid-from`（なければ今日）の時点の文言に `quote` が含まれること。29 規範すべてで一致 |

### 時点と経過措置

改正前後で規定が変わった規範には `valid-from: 2020-04-01` と `time-anchor` をつけ、平成29年法律第44号の附則に従って「どの時点で判定するか」を決めました。

| time-anchor | 時点 | 附則 | 使っている規範 |
|-------------|------|------|---------------|
| `declaration` | 意思表示の時 | 6条1項 | 93条、95条、96条2項 |
| `contract` | 契約締結の時 | 34条1項 | 557条 |
| `claim-arose` | 債権が生じた時（原因である法律行為の時を含む） | 10条1項・4項 | 145条、147条、152条、166条 |

時点が施行日より前の事案では、改正後の規範を適用せず、報告に「この時点に適用される規範（旧法など）は未登録」と警告を出します。旧法の規範はフェーズ3で登録します。

## 8.4 コンパイラ

[src/legal_onto/compiler.py](../../src/legal_onto/compiler.py)。規範 N ごとに 2 つの関数を生成します。

| 関数 | 意味 | 生成のしかた |
|------|------|-------------|
| `c_N($c)` | 要件を満たす | 要件の木（all → 連結、any → `or`、規範 → その `h_` 関数）＋ 適用期間の条件 |
| `h_N($c)` | 成立する | `c_N` を満たし、N に対する例外がどれも成立しない（`not { let $z in h_E($c); }`） |

阻止の抗弁（同時履行の抗弁）は請求原因の `h_` では否定せず、結論の関数で「引換給付」として扱います。

| 結論の関数 | 意味 |
|-----------|------|
| `ground_holds($c)` | 請求原因が成立し、消滅・障害の抗弁が成立しない |
| `blocked($c)` | 阻止の抗弁が成立する |
| `claim_granted($c)` | 請求を認める |
| `claim_granted_in_exchange($c)` | 引換給付で請求を認める |

生成例（錯誤の再抗弁）:

```typeql
  # R95-3 表意者の重大な過失（要件）
  fun c_r95_3($c: claim) -> { claim }:
  match
    $c isa claim;
    $tp isa time-point, links (subject: $c), has anchor-code "declaration", has at $t; $t >= 2020-04-01;
    $f1 isa fact-finding, links (subject: $c), has fact-code "N95-3.gross-negligence"; let $f1 in established();
  return { $c };

  # R95-3 表意者の重大な過失（成立）層2
  fun h_r95_3($c: claim) -> { claim }:
  match
    let $y in c_r95_3($c);
    not { let $z0 in h_e95_3($c); };
  return { $c };
```

再コンパイルでは、前回定義した関数（`compiled-function` に記録）を `undefine` してから定義し直します。生成される TypeQL は `legal-onto compile` で確認できます。

## 8.5 評価と報告

`legal-onto evaluate cases/demo-001.yaml` は、事案を取り込んで結論の関数で評価し、規範ごとの関数の結果から報告を組み立てます。報告には [06](06-decisions.md#64-出力の約束実務家向け) の約束どおり、次の内容を含めます。

1. 結論と理由（成立した抗弁など）
2. 論証の木: 争点になっている規範ごとに、成立・不成立、層、証明責任、要件事実の証明状態
3. 結論を変えうる立証: 対象の規範の要件が満たされているのに、自分の要件が満たされていない規範について、証明されていない要件事実と証明責任を負う側
4. 注意: 未入力の時点、適用期間外の規範、専門家の確認を経ていない規範、利用者の評価に依存する規範的要件
5. 法的判断は利用者が行う旨の表示

「争点になっている規範」は、その規範に固有の要件事実（他の規範と共有しないもの）が 1 つでも入力されている規範です。「取消しの意思表示」のように複数の抗弁に共通する事実だけでは、詐欺・強迫などの抗弁を表示しません。

提案書 4.5 の例題の報告（抜粋）:

```
■ 訴訟物 demo-001-price（sale-price）: X → Y
  結論: 請求を認める
  論証（事実が入力された規範のみ表示）:
    [成立] G555-price 売買代金支払請求（請求原因・立証責任: 請求する側）
      [要件充足・例外により不成立] D95 錯誤による取消し（抗弁・立証責任: 請求される側）
        [成立] R95-3 表意者の重大な過失（再抗弁・立証責任: 請求する側）
          [不成立] E95-3 相手方の悪意・重過失又は共通錯誤（再々抗弁・立証責任: 請求される側）
              次のいずれか:
                ? 請求する側が、錯誤を知り、又は重大な過失によって知らなかったこと［真偽不明、規範的要件: 評価は利用者の入力］
  結論を変えうる立証:
    - 請求される側: 請求する側が、錯誤を知り、又は重大な過失によって知らなかったこと［真偽不明］（E95-3）
  注意:
    ! 専門家の確認を経ていない規範を使っている: G555-price（unreviewed）、D95（unreviewed）、NR95（unreviewed）、R95-3（unreviewed）
    ! 利用者の評価に依存する規範的要件: その錯誤が…重要なものであること、錯誤が…重大な過失によるものであったこと
```

## 8.8 TypeDB 3.13 で分かったこと（7.5 の続き）

| 事項 | 内容 | 対応 |
|------|------|------|
| 引数のない関数を否定の中で呼ぶ | 呼ぶたびに全件を評価し直し、件数 × 否定の数に比例して遅い | 訴訟物を引数にとる関数にする（8 分半 → 19 秒） |
| 複数の否定で同じ変数名 | `not { let $z in f($c); }; not { let $z in g($c); };` は REP44 になる | 否定ごとに変数名を変える |
| 所有の多重度 | `owns` の既定は `@card(0..1)` | 典拠のように複数持つ属性は `@card(0..)` |
| 1 つだけの `{ … }` | `or` のない単独の `{ … }` は構文エラー | 分岐が 1 つなら波括弧をつけない |
| 属性と値の比較 | 関数の引数（値）を `has fact-code $code` に直接使うと REP35 | 属性を別の変数で受け、`==` で比べる |
