# 5. 進め方・検証・リスク

## 5.1 段階的な進め方

| フェーズ | 目標 | 主な成果物 | 完了条件 |
|---------|------|-----------|---------|
| 0. 範囲の確定 | 対象分野と問いを決める | 対象条文の一覧、代表的な問い（クエリ）10〜20 件 | 民法の意思表示（93〜98条の2）・売買（555条以下）・消滅時効（144条以下）で合意 |
| 1. 基盤と条文層（**完了**: [07](07-phase1-results.md)） | TypeDB 3.x 環境と法令の取り込み | スキーマ（4.1）、e-Gov 法令API v2 からの取り込みスクリプト、参照関係の抽出 | 民法全体を時点を指定して取り込め、準用・参照の再帰クエリが動く。本提案の TypeQL の構文を実機で検証済み |
| 2. 規範層とコンパイラ（**完了**: [08](08-phase2-results.md)） | 手作業で規範化し、関数を生成する | 規範データ（20〜40 規範）、コンパイラ、テスト事案 | 例題（4.5）を含むテスト事案で、期待する結論・不足事実が得られる |
| 3. 説明・時点・見解 | 説明可能性と比較クエリ | 実体化パス、導出記録、旧95条の規範、見解タグ | Q1〜Q4（4.5）が動く。2020年改正の前後で結論の違いを示せる |
| 4. 作成支援 | 規範・事実の抽出を半自動化する | LLM による条文 → 規範候補、事案の叙述 → 事実候補の抽出と、レビュー画面 | 抽出候補の人によるレビューの採択率を測定できる |
| 5. 拡張 | 分野の拡大と高度な推論 | 契約各則・不法行為への拡大、必要に応じて外部の論証エンジン（ASP など）との連携 | 規則の衝突（特別法と一般法など）を含む事案を扱える |

## 5.2 検証方法

1. **単体テスト（事案テスト）**: 規範ごとに「全要件が証明済」「要件の一部が真偽不明」「例外が成立」「例外の例外が成立」の事案を作り、期待される結論を確かめます。要件事実の教材にある設例を、そのまま回帰テストにできます。
2. **PROLEG との突き合わせ**: 同じ規範・事実を PROLEG で評価し、結論が一致することを確かめます（推論の意味論の正しさの検証）。
3. **COLIEE データ**: 民法の短答問題のうち、規範化した範囲に入る問題で正答率を測ります（規範化の網羅性・正確さの検証）。
4. **法律家のレビュー**: 規範層の内容（要件の立て方、証明責任の配分、見解の帰属）は、法律の専門家に確認してもらいます。
   - → 専門家は確保できないことになりました。代替策（典拠の明記・PROLEG との突き合わせ・利用者によるレビュー）は [06](06-decisions.md#62-専門家レビューの代替策) にまとめています。

## 5.3 リスクと対策

| リスク | 内容 | 対策 |
|-------|------|------|
| 規範化のコスト | 条文から規範への変換は専門知識を要し、量も多い | 対象を絞って始める。PROLEG の規則を参考にする。フェーズ4で LLM による候補抽出を導入する |
| 開かれた構造（open texture） | 「重大な過失」「正当な理由」などの評価は機械的に決まらない | 規範的要件は `evaluative` として印をつけ、評価結果を人が入力する。システムは「評価が必要な点」と評価根拠事実・評価障害事実を提示するにとどめる |
| 解釈の対立 | 判例・学説で要件が分かれる | 見解タグで規範を並存させ、比較クエリで違いを示す。既定の見解は判例とする |
| TypeDB 関数の制約 | 層化否定のみ、データを書けない、導出過程を返さない | コンパイラによる層化の検査、実体化パスによる導出記録。非層化の衝突解決が必要になったら外部エンジン（方式D）を追加する |
| TypeDB の仕様変更 | 3.x の関数仕様はまだ発展途上 | フェーズ1で実機検証する。コンパイラの出力部分を切り替えやすく作る |
| 時間的な管理の複雑さ | 改正・経過措置・行為時法 | 条文の版と規範の有効期間を分けて管理する。経過措置自体も規範として表す |
| 専門家レビューの不在 | 実務家の支援用だが、規範層を事前にレビューする専門家がいない | 典拠のない規範は登録しない。レビュー状態を規範に持たせ、未確認の規範を使った結論には必ずその旨を表示する（[06](06-decisions.md)） |
| 法的な責任 | 個別事案に対する法的判断の提供は、弁護士法72条（非弁行為）などに抵触しうる | 研究・教育・専門家の業務支援の用途に位置づける。出力には根拠と前提（採用した見解・事実の証明状態）を必ず添え、最終判断は専門家が行う前提を明示する |

## 5.4 まず決めること

着手前に、次の点について方針を決める必要があります。

> 決定済み（2026-10-02）: 実務家の支援用、民法の意思表示・売買・消滅時効、docker compose によるローカルの TypeDB CE と Python、専門家レビューなし。詳細は [06](06-decisions.md)。

1. **用途**: 研究・教育用（要件事実の学習支援）か、実務家の支援用か。説明の粒度と求められる正確さが変わります。
2. **対象分野**: 本提案では民法（意思表示・売買・時効）を推奨しています。刑法（犯罪論体系）や行政法を優先する場合は、証明状態の扱いと裁量の表現を先に設計します。
3. **TypeDB の版と実行環境**: TypeDB 3.x（Community Edition / Cloud）のどちらを使うか。
4. **規範作成の体制**: 規範層をレビューする法律の専門家を確保できるか。
