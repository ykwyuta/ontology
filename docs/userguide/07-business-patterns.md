# 第7章 オントロジーが効く場面

オントロジーは万能ではありません。この章では、ビジネスで効果が出やすい典型的な場面（パターン）と、逆に普通の RDB で十分な場面を整理します。

## 7.1 効果が出やすい 5 つのパターン

| パターン | 困りごと | オントロジーで何が変わるか |
|---------|---------|------------------------|
| データ統合 | システムごとに同じものの呼び方・意味が違う | 共通の概念と ID を橋渡しにする |
| 意味検索・探索 | キーワードが一致しないと見つからない。関係をたどれない | 概念の階層や関係をたどって探せる |
| ルール判定と説明 | 判定ロジックがコードに散らばり、根拠を説明できない | ルールをモデルに集め、結論と根拠を一緒に返す |
| 影響分析 | 何かを変えたとき、どこに影響が出るかわからない | 依存関係をグラフでたどる |
| AI の根拠づけ | 生成 AI の回答がもっともらしいが正しいとは限らない | 正確な知識を AI に渡し、回答を検証する |

### パターン1: データ統合

第6章で見たように、システムごとにバラバラな「顧客」「製品」「取引」を、共通の概念で結びます。全データを1か所に集める（データレイク）だけでは、「何が同じで、何が違うか」は解決しません。オントロジーはその意味の層を担います。

**向いている状況**: M&A でシステムが統合される、グループ会社のデータを横断分析したい、外部データ（公開データ、取引先のデータ）と自社データを組み合わせたい。

### パターン2: 意味検索・探索

「心臓の病気」で検索したときに、「心筋梗塞」「狭心症」の文書も見つけたい。これは、病名の階層（心筋梗塞は心臓の病気の一種）を知っていればできます。また「この部品を使っている製品の、主な顧客」のように、関係を何段もたどる問い合わせは、グラフ型のデータで得意な処理です。

**向いている状況**: 専門用語の多い文書検索（医療、法務、特許、技術文書）、推薦（この商品を買った人が関心を持ちそうな関連商品）、調査業務（取引関係の調査、不正の検知）。

### パターン3: ルール判定と説明

与信審査、保険の支払い判定、補助金の受給資格、法令の適合性チェックなど、**条件が何段にも重なり、例外が多い判定**です。ルールをモデルに集めると、

- 業務担当者がルールを読んで確認できる
- 結論だけでなく「どのルールの、どの条件が満たされた（満たされなかった）か」を説明できる
- 「どの事実がそろえば結論が変わるか」を示せる

ようになります。このリポジトリは、まさにこのパターンを民法で試しています（第5部）。

### パターン4: 影響分析

「この規程を変えたら、どの業務手順に影響するか」「この部品の供給が止まったら、どの製品の出荷が止まるか」「このテーブルの列を消したら、どのレポートが壊れるか」。依存関係をグラフで持っていれば、推移的にたどって影響範囲を出せます。

**向いている状況**: 規程・法令の改正対応、サプライチェーンのリスク管理、データの来歴（リネージ）管理、システムの変更影響調査。

### パターン5: AI の根拠づけ

生成 AI に社内の知識を答えさせるとき、正確な事実や関係を知識グラフから取り出して渡すと、回答の正確さと説明可能性が上がります（第19章）。

## 7.2 普通の RDB で十分な場面

次のような場合は、オントロジーを持ち込む必要はあまりありません。

| 状況 | 理由 |
|------|------|
| データの種類が少なく、意味が明確 | 在庫数、受注明細など。テーブル設計で十分に表せる |
| 1 つのシステムで閉じている | 意味を共有する相手がいない |
| ルールが単純で、変更もまれ | コードに書いても困らない |
| 大量の数値の集計が中心 | 分析用 DB（列指向 DB、DWH）のほうが向いている |
| 高頻度の更新トランザクション | 受発注、決済などは RDB が得意 |

実際には、**基幹のトランザクションは RDB に残し、その上に意味の層としてオントロジーを重ねる**構成がよく取られます。オントロジーで全部を置き換える必要はありません。

## 7.3 効果をどう測るか

オントロジーの導入効果は見えにくいので、導入前に測り方を決めておきます。

| パターン | 測る指標の例 |
|---------|------------|
| データ統合 | 新しい分析に必要なデータ準備の工数、名寄せの手作業の件数 |
| 意味検索 | 検索の再現率（見つけるべきものを見つけた割合）、調査にかかる時間 |
| ルール判定 | 判定のやり直し・問い合わせの件数、ルール変更の反映にかかる日数 |
| 影響分析 | 影響調査にかかる時間、見落としによる障害の件数 |
| AI の根拠づけ | 回答の正答率、根拠を示せた回答の割合 |

## 7.4 判断のためのチェックリスト

次のうち 2 つ以上当てはまれば、オントロジーを検討する価値があります。

- [ ] 「これとこれは同じものか」を人が判断する作業が日常的にある
- [ ] 同じ言葉が部署によって違う意味で使われている
- [ ] 関係を 3 段以上たどる問い合わせがよくある
- [ ] 判定ルールが多く、例外が多く、よく変わる
- [ ] 判定や回答の根拠を説明する必要がある（監査、顧客対応、規制）
- [ ] 変更の影響範囲の調査に時間がかかっている
- [ ] 生成 AI に社内の知識を正確に答えさせたい

## まとめ

- オントロジーが効くのは、データ統合、意味検索、ルール判定と説明、影響分析、AI の根拠づけ
- 単純で閉じたシステム、集計中心、高頻度の更新処理には RDB が向いている
- 基幹は RDB に残し、その上に意味の層を重ねる構成が現実的
- 導入前に、効果を測る指標を決めておく
