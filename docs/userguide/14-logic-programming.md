# 第14章 論理プログラミング（Datalog・Prolog）

論理プログラミングは、**事実とルールだけ**でプログラムを書く方式です。データベースというより「推論エンジン」ですが、オントロジーの推論部分を担う方式として重要で、法律の分野ではとくに長い歴史があります。

## 14.1 事実とルール

論理プログラミングでは、2 種類の文だけを書きます。

| 種類 | 書き方 | 意味 | RDB でいうと |
|------|-------|------|------------|
| 事実 | `member_of("山田", "第一営業部").` | これは正しい | テーブルの行 |
| ルール | `A :- B, C.` | B かつ C なら A | ビュー |

`:-` は「もし〜ならば」と読みます（左が結論、右が条件）。大文字で始まる語は変数です。

## 14.2 例題を Datalog で書く

Datalog は、Prolog から関数記号などを除いて、必ず計算が終わるようにした言語です。データベースの問い合わせ言語として研究されてきました。ここでは一般的な書き方で示します（Soufflé などの処理系では、宣言の書き方が少し違います）。

```prolog
% --- 事実 ---
regular_employee("山田").   contract_employee("佐藤").
regular_employee("鈴木").   regular_employee("田中").

sub_of("第一営業部", "営業本部").
sub_of("第二営業部", "営業本部").
department("営業本部"). department("第一営業部").
department("第二営業部"). department("開発部").

member_of("山田", "第一営業部").  member_of("佐藤", "第一営業部").
member_of("鈴木", "第二営業部").  member_of("田中", "開発部").

% 割り当て(社員, プロジェクト, 役割, 開始日)  ← 4 項の関係をそのまま書ける
assignment("山田", "X", "leader", "2026-04-01").
assignment("佐藤", "X", "member", "2026-04-15").
assignment("鈴木", "Y", "leader", "2026-05-01").

% --- ルール ---
% 継承: 正社員も契約社員も社員
employee(E) :- regular_employee(E).
employee(E) :- contract_employee(E).

% 推移的な関係: D は A の配下（自分自身を含む）
within(D, D) :- department(D).
within(D, A) :- sub_of(D, P), within(P, A).

% Q1
in_sales_hq(E) :- employee(E), member_of(E, D), within(D, "営業本部").

% Q2: リーダーは同じプロジェクトの他のメンバーを承認できる
can_approve(L, M) :- assignment(L, P, "leader", _), assignment(M, P, _, _), L != M.

% Q3: 否定
assigned(E)   :- assignment(E, _, _, _).
unassigned(E) :- employee(E), not assigned(E).
```

継承もルール、推移的な関係もルール、問いの答えもルールです。**すべてが同じ形で書ける**のが論理プログラミングの強みです。述語には何個でも引数を持たせられるので、4 項の「割り当て」もそのまま書けます。

## 14.3 否定と層化

`unassigned(E) :- employee(E), not assigned(E).` の `not` は、「`assigned(E)` を導けなければ」という意味です（失敗による否定、閉世界。第5章）。

Datalog の処理系は、`assigned` を先に全部計算してから `unassigned` を計算します。これが**層化**です。もし `assigned` の定義の中で `unassigned` を否定で使うと循環になるので、処理系はエラーにします。

## 14.4 法律と論理プログラミング: PROLEG

論理プログラミングは、法律の推論を表す方式として古くから研究されてきました。1980 年代には、英国国籍法を Prolog で書いた研究がよく知られています。

日本では、国立情報学研究所の佐藤健氏らが、**要件事実論**（民事訴訟で、誰が何を主張・立証すべきかを整理する理論）を論理プログラムで表した **PROLEG** を開発しています。PROLEG では、法律の規定を「原則のルール」と「例外」に分けて書きます。次は考え方を示すための簡略化した例です（実際の PROLEG の構文とは異なる部分があります）。

```prolog
% 原則: 売買契約が成立していれば、代金を請求できる
price_claim(C) <= contract_concluded(C).

% 例外: 錯誤による取消しが成り立てば、原則の効果は生じない
exception(price_claim(C), cancelled_by_mistake(C)).

% 取消しの原則
cancelled_by_mistake(C) <= mistake(C), material(C), cancellation_declared(C).

% 取消しの例外（重大な過失）、その例外（相手方が知っていた）
exception(cancelled_by_mistake(C), gross_negligence(C)).
exception(gross_negligence(C), counterparty_knew(C)).
```

「原則が成り立ち、かつ例外が成り立たなければ、効果が生じる」という評価のしかたは、層化否定と同じです。そして「例外が成り立たない」を「例外の事実が証明されていない」と読めば、証明責任の考え方（第5章）とも一致します。このリポジトリの規範層は、この考え方を TypeDB の上で再現したものです（第24章・第25章）。

## 14.5 ASP（解集合プログラミング）

Datalog の層化否定では書けない問題（ルール同士が互いに否定し合う、どちらを選んでもよい選択肢がある）を扱える方式に、ASP（Answer Set Programming）があります。clingo などの処理系があります。

法律の分野では、「特別法と一般法のどちらを優先するか」「判例の立場と学説の立場」のように、互いに衝突するルールの扱いを研究する際に使われます。このリポジトリの提案書でも、層化否定で扱えない衝突が出てきたときの拡張先として挙げています。

## 14.6 データベースとしての論理プログラミング

論理プログラミングは、単独のデータベース製品として使われることは多くありません。主な使われ方は次のとおりです。

| 使われ方 | 例 |
|---------|-----|
| 推論エンジンとして、他のデータベースのデータを読み込んで推論する | Soufflé（プログラム解析などで使われる高速な Datalog 処理系） |
| データベースの問い合わせ言語として | Datomic の問い合わせ言語（Datalog ベース） |
| 他の方式の推論部分の理論的な土台として | SPARQL の推論、TypeDB の関数、RDB の再帰 CTE はいずれも Datalog と関係が深い |

## 14.7 得意なことと苦手なこと

| 得意 | 苦手 |
|------|------|
| ルールが主役。推論を最も素直に書ける | 大量データの保存・更新・トランザクションは不得意（別のデータベースと組み合わせる） |
| n 項の関係をそのまま書ける | スキーマ・型の仕組みが弱い（処理系による） |
| 理論が明確（層化否定、ASP の安定モデルなど） | 書ける人が少ない |
| 法律のルールとの相性がよい（PROLEG など） | 業務システムとの連携の部品が少ない |

## まとめ

- 論理プログラミングは、事実とルールだけで書く。継承も推移性も問いの答えもルールになる
- 否定は「導けなければ偽」（閉世界）で、層化して評価する
- 法律の「原則と例外」は論理プログラミングと相性がよく、PROLEG は要件事実論をこの方式で表している
- 実務では、推論エンジンとして他のデータベースと組み合わせて使うことが多い

| 観点 | 論理プログラミング |
|------|-----------------|
| スキーマ | 弱い（処理系により型宣言あり） |
| 継承 | ルールで書く |
| n 項関係 | そのまま書ける |
| 推移的な関係 | 再帰ルール |
| ルール | 主役 |
| 否定 | 失敗による否定（閉世界）。層化、ASP |
| 標準化 | ISO Prolog あり。Datalog は処理系ごと |
