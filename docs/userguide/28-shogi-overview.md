# 第28章 将棋のルールをオントロジーにする

第5部では民法を扱いました。第6部では、同じリポジトリで行ったもう一つの試み、**将棋のルールを TypeDB で表し、AI が提案した指し手がルールに合っているかを判定する仕組み**を読み解きます。この章では、なぜ将棋なのか、ルールをどうデータにしたかを見ます。

## 28.1 なぜ将棋か

民法の試みには、大きな弱点がありました。ルール（規範）が正しいかを確かめる専門家がいないことです（第21章、第24章）。将棋は、この点で対照的です。

| 観点 | 民法 | 将棋 |
|------|------|------|
| ルールの構造 | 原則と例外（請求原因・抗弁・再抗弁） | 駒の動き（原則）と禁じ手（例外） |
| 正しさの確認 | 専門家のレビューが必要 | 既存の将棋ライブラリと**機械的に**比べられる |
| 判定の対象 | 事案（事実と証明状態） | 局面と指し手 |
| AI との関係 | AI の回答の根拠づけ | AI の指し手の検査 |

つまり将棋は、**「AI の出力をルールで検査し、反したら理由を返す」仕組みを、正解のある環境で作り込める**題材です。ここで作った仕組み（反則ごとの判定関数、根拠つきの判定結果、提案と判定のループ）は、法律や業務ルールの判定にもそのまま使えます。

用途は、次の 2 つに決めました。

- **AI 対局の審判**: AI 同士・AI と人の対局で、1 手ごとに合法かを判定し、対局の終了（詰み・反則・千日手など）を判定する
- **LLM のルール理解の評価**: LLM に指させて、どのルールをどれくらい破るかを測る

## 28.2 将棋のルールを分解する

将棋のルールを、オントロジーの部品（第1部）に分けると次のようになります。

| ルール | オントロジーの部品 | 例 |
|-------|----------------|-----|
| 盤（9×9 のマス） | インスタンスと関係（データ） | 81 マスと、マスどうしの位置関係 |
| 駒の種類と動き | クラスと属性（データ） | 金は 6 方向に 1 マス、飛車は縦横に何マスでも |
| 成り | 関係（データ） | 歩 → と金、角 → 馬 |
| 敵陣、行き所のない段 | 関係（データ） | 先手の敵陣は一〜三段、歩は先手なら一段目にいられない |
| 利き・合法手 | 推論（関数） | 飛車は途中の駒で止まる（推移的な関係、第4章） |
| 禁じ手 | 例外のルール（関数） | 二歩、打ち歩詰め、王手放置 |

ポイントは、**ルールの大半がデータで書ける**ことです。駒の動きをコードの `if` 文で書く代わりに、表として持ちます。

## 28.3 盤をデータにする

最初の試作では、マスを座標（筋 5、段 5）で表し、「右に 1 マス」を `筋 + 1` という計算で求めていました。ところが TypeDB 3.13 では、整数を返す関数の中で `or` を使うと型の検査でエラーになりました（第30章）。

そこで発想を変え、**盤そのものをデータにしました**。

```typeql
entity square, owns square-id @key, owns file, owns rank, ...;          # 81 マス
relation geometry, relates origin, relates target, owns df, owns dr;   # origin から (df, dr) ずれたマスが target
```

81 マスのそれぞれについて、8 方向と桂馬の 4 方向の「隣のマス」を関係として持ちます（約 900 件）。「5五の右上のマス」は、計算ではなく関係をたどって求めます。

RDB でいえば、座標を計算する代わりに「隣接表」というテーブルを作っておくのと同じ発想です。データを増やす代わりに、問い合わせが単純になります。盤の大きさが違う将棋の変種にも、データを入れ替えるだけで対応できます。

## 28.4 駒の動きをデータにする

駒の種類ごとに、動き（方向と、何マスでも進めるか）を持たせます。

```typeql
entity piece-type, owns piece-code @key, owns piece-name, ...;
entity step, owns df, owns dr, owns slides;          # 方向と、何マスでも進めるか
relation movement, relates piece, relates step;
relation promotion, relates base, relates promoted;  # 歩 → と金 など
```

| 駒 | 動き（先手の向き。前は dr = −1） |
|----|-------------------------------|
| 金 | (−1,−1) (0,−1) (1,−1) (−1,0) (1,0) (0,1)、どれも 1 マス |
| 飛車 | 縦横 4 方向、何マスでも |
| 竜（成った飛車） | 縦横 4 方向は何マスでも、斜め 4 方向は 1 マス |
| 桂馬 | (−1,−2) (1,−2)、1 マス（間の駒を飛び越える） |

後手は向きが逆なので、プレイヤーに `sign`（先手 1、後手 −1）を持たせ、方向に掛けます。Java でいえば、駒ごとに `move()` メソッドをオーバーライドする代わりに、動きの表を 1 つの汎用的な関数で解釈する、データ駆動の設計です。

## 28.5 利き: 再帰で駒の動きを求める

飛車・角・香車は、途中に駒があるところで止まります。これを再帰関数で書きます（第4章の推移的な関係）。

```typeql
# $s から ($df, $dr) の方向に進んで届くマス（最初にぶつかった駒のマスを含む）
fun ray($p: position, $s: square, $df: integer, $dr: integer) -> { square }:
match
  { let $t in next_square($s, $df, $dr); } or
  { let $m in next_square($s, $df, $dr); let $t in ray_beyond($p, $m, $df, $dr); };
return { $t };

# 空きマスなら、その先へ進む
fun ray_beyond($p: position, $m: square, $df: integer, $dr: integer) -> { square }:
match
  not { occupancy (position: $p, square: $m); };
  let $t in ray($p, $m, $df, $dr);
return { $t };
```

「隣のマスは届く」「隣が空いていれば、その先も届く」という 2 行の定義で、何マス先までも求められます。否定（`not`）を別の関数に分けているのは、`or` の分岐の中で否定を使うと TypeDB がエラーにするためです（民法のときと同じ回避策です）。

## 28.6 局面

局面は、駒の配置・持ち駒・手番の 3 つの関係で表します。

```typeql
relation occupancy, relates position, relates square, relates piece, relates owner;   # 駒の配置
relation in-hand, relates position, relates piece, relates owner, owns amount;       # 持ち駒
relation turn, relates position, relates player;                                     # 手番
```

「駒の配置」は、局面・マス・駒の種類・持ち主の **4 者を結ぶ関係**です（第3章の n 項関係）。RDB なら `(position_id, square_id, piece_code, owner)` の 4 列を持つ中間テーブルにあたります。

局面は、将棋ソフトで標準的に使われる SFEN という 1 行の文字列から作ります。

```
lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b - 1     ← 初期局面
```

## まとめ

- 将棋は、ルールが明確で正解を機械的に確かめられるので、「AI の出力をルールで検査する」仕組みの検証台に向いている
- 盤・駒の動き・成り・敵陣は、データ（インスタンスと関係）で表せる
- 盤を「隣のマス」の関係として持つと、座標の計算が要らなくなる
- 飛び駒の利きは、再帰関数（推移的な関係）で求める
