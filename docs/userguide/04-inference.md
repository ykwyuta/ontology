# 第4章 推論: 書いていない事実を導く

オントロジーを使う一番の理由は、**保存していない事実を、モデルに書いたルールから導ける**ことです。これを推論と呼びます。この章では、推論の種類と、SQL のビューや Java のメソッドとの違いを説明します。

## 4.1 推論とは

次のデータがあるとします。

- 山田さんは正社員である
- 正社員は社員の一種である（サブクラス関係）

「山田さんは社員か？」と聞かれたら、データには「山田さんは社員である」とは書いてありませんが、答えは「はい」です。これが推論です。

推論は大きく3種類に分けられます。

| 種類 | 何から導くか | 例 |
|------|------------|-----|
| 分類による推論 | クラスの階層 | 正社員 → 社員 |
| 関係の性質による推論 | 推移性・対称性など | ネジ → エンジン → 車 なので、ネジは車の部品 |
| ルールによる推論 | 「AかつBならC」という規則 | 売上が 100 万円超かつ取引 3 年以上なら優良顧客 |

## 4.2 分類による推論

第2章で見たとおり、サブクラス関係を書いておけば、親クラスで問い合わせたときに子クラスのインスタンスも返ります。

もう一歩進んで、**条件で定義されたクラス**を作ることもできます。

```
優良顧客 = 顧客 のうち、年間売上 が 100万円 を超えるもの
```

この定義があれば、優良顧客のフラグを保存しなくても、条件を満たす顧客は自動的に優良顧客として扱われます。売上が変われば、分類も自動で変わります。

Java でいえば、`isPremium()` メソッドを書くのに近いですが、違いがあります。

- Java のメソッドは、オブジェクトを取り出してから呼ぶものです。「優良顧客を全員探す」には、全顧客を取り出してループする必要があります
- オントロジーの定義は、データベースへの問い合わせの中で使えます。「優良顧客を全員」と聞けば、データベースが条件で絞り込んで返します

## 4.3 関係の性質による推論

部品表（BOM）を例にします。

| 部品 | 親部品 |
|------|--------|
| ネジ A | エンジン |
| エンジン | 車 |
| ピストン | エンジン |

「車を構成する部品をすべて」と聞かれたら、エンジン・ネジ A・ピストンが答えです。RDB では再帰 CTE を書きます。

```sql
WITH RECURSIVE parts(part) AS (
  SELECT part FROM bom WHERE parent = '車'
  UNION
  SELECT b.part FROM bom b JOIN parts p ON b.parent = p.part
)
SELECT part FROM parts;
```

オントロジーでは「部品である」という関係を推移的と宣言しておけば、「車の部品」と聞くだけで、データベースが階層をたどってくれます。問い合わせる人は、階層が何段あるかを気にする必要がありません。

## 4.4 ルールによる推論

もっとも強力なのが、「条件がそろえば、この結論が成り立つ」というルールです。

```
ルール: 割り当て(社員 E, プロジェクト P, 役割 リーダー)
        かつ 割り当て(社員 F, プロジェクト P, 役割 *)
        ならば 承認できる(E, F)
```

「プロジェクトのリーダーは、そのプロジェクトのメンバー全員の作業を承認できる」というルールです。このルールがあれば、「山田さんが承認できる人は誰か」という問い合わせに、データベースが答えます。

### ルールを組み合わせる

ルールの結論を、別のルールの条件に使えます。

```
ルール1: 正社員 かつ 等級 が 5 以上 ならば 管理職
ルール2: 管理職 かつ 部署 の 長 ならば 決裁者
```

決裁者を探すと、ルール2がルール1の結果を使います。業務ルールが何段にも重なる分野（人事、与信、保険、法律）で、この力が発揮されます。

## 4.5 SQL のビュー、Java のメソッドとの違い

ルールは SQL のビューや Java のメソッドでも書けます。違いはどこにあるのでしょうか。

| 観点 | SQL のビュー | Java のメソッド | オントロジーのルール |
|------|------------|---------------|-------------------|
| 書く場所 | データベース | アプリケーション | モデル（データベース） |
| 再帰 | 再帰 CTE で可能だが書きにくい | 可能 | 自然に書ける |
| 組み合わせ | ビューの上にビュー | メソッドの呼び出し | ルールの結論を別のルールで使う |
| 問い合わせへの組み込み | できる | できない（取り出してから計算） | できる |
| 誰が読めるか | SQL がわかる人 | Java がわかる人 | モデルを読める人（業務担当者と共有しやすい） |
| 根拠の説明 | 難しい | ログを仕込めば可能 | 「どのルールで導いたか」を追いやすい |

一番の違いは、**ルールが業務の言葉で、1 か所にまとまっている**ことです。ビューやメソッドに散らばったルールは、何年か経つと誰も全体を把握できなくなります。オントロジーにルールを集めておけば、「このルールはどこで使われているか」「このルールを変えると何が変わるか」を調べられます。

## 4.6 推論の方式: 前もって計算するか、聞かれてから計算するか

推論の結果を、いつ計算するかには2つのやり方があります。

| 方式 | 動き | 長所 | 短所 |
|------|------|------|------|
| 前向き（実体化） | データが入った時点でルールを適用し、結果を保存する | 問い合わせが速い | データが変わるたびに計算し直す。保存量が増える |
| 後ろ向き（問い合わせ時） | 問い合わせが来たときに、必要なルールだけ適用する | 常に最新。保存量が増えない | 問い合わせが遅くなることがある |

SQL でいえば、前向きはマテリアライズドビュー、後ろ向きは普通のビューです。このリポジトリでは、問い合わせ時に TypeDB の関数で推論し、説明に使う結果だけをあとから保存する（実体化する）組み合わせを計画しています（第25章）。

## 4.7 推論の注意点

- **ルールが循環しないようにする**: 「AならB」「BならA」のようなルールは、答えが決まらなかったり、計算が終わらなかったりします
- **否定に気をつける**: 「〜でなければ」というルールは便利ですが、扱いを間違えると結果が不安定になります（第5章）
- **ルールの数が増えると、なぜその結論になったかがわかりにくくなる**: 結論だけでなく「どのルールを、どの事実に当てはめたか」を示す仕組みを用意します（第26章）

## まとめ

- 推論とは、保存していない事実を、モデルに書いた分類・関係の性質・ルールから導くこと
- ルールは組み合わせられ、業務ルールが何段にも重なる分野で力を発揮する
- ビューやメソッドとの違いは、ルールが業務の言葉で1か所にまとまり、問い合わせに組み込め、根拠を追えること

| 概念 | RDB | Java | オントロジー |
|------|-----|------|------------|
| 条件で決まる分類 | ビュー | `isXxx()` メソッド | 条件で定義したクラス |
| 階層をたどる | 再帰 CTE | 再帰メソッド | 推移的な関係 |
| 業務ルール | ストアド・ビュー・アプリ | サービスクラス | ルール（モデルの一部） |
| 結果の保存 | マテリアライズドビュー | キャッシュ | 実体化 |
