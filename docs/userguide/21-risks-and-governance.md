# 第21章 リスクと統制

AI とオントロジーを組み合わせたシステムは、うまく作れば正確で説明可能になりますが、作り方を誤ると「正しそうに見える誤り」を大量に生みます。この章では、主なリスクと、それを抑える仕組みを整理します。

## 21.1 主なリスク

| リスク | 内容 | 例 |
|-------|------|-----|
| もっともらしい誤り | LLM が作ったルールや事実が、形は正しいが中身が誤っている | 証明責任を逆に配分した規範、存在しない判例 |
| 誤りの固定化 | 誤ったルールがモデルに入ると、以後のすべての判定に影響する | 1 つの規範の誤りが、全事案の結論を変える |
| 検証できない出力 | 結論だけが出て、なぜそうなったか確かめられない | 判定理由の説明がない |
| 適用範囲の取り違え | モデルが扱っていない範囲でも結論を出してしまう | 改正前の事案に、改正後のルールを当てはめる |
| レビューの形骸化 | 候補が多すぎて、確認が形だけになる | 全件を「確認済み」にする |
| 責任の所在があいまい | 誰の判断で結論が出たのかわからない | 「システムがそう言った」 |
| 法規制 | 業務の内容によっては、資格のない者が個別の判断を示すことが規制される | 法律相談（日本では弁護士法 72 条） |

## 21.2 抑える仕組み

### 仕組み1: 確認の状態を持たせる

ルール（規範）ごとに、誰がどこまで確認したかを状態として持たせます。このリポジトリでは 5 つの状態を使っています。

| 状態 | 意味 |
|------|------|
| unreviewed | 登録直後。誰も確認していない |
| source-checked | 典拠（教科書・条文）と照合済み |
| proleg-matched | 別のシステム（PROLEG）と結論が一致 |
| user-confirmed | 利用者（実務家）が利用時に確認 |
| disputed | 疑義あり。解消するまで警告を出す |

### 仕組み2: 典拠のないルールは登録しない

ルールには必ず典拠（根拠となる条文、規程、文献）を付け、典拠のないルールは読み込みの段階で拒否します。典拠が原文の引用なら、機械で照合します（第18章）。

### 仕組み3: 自動検証を重ねる

| 検証 | 見つけられる誤り |
|------|---------------|
| 形式・参照の検査 | 書き間違い、存在しない参照 |
| 原文との照合 | 存在しない条文・文言（ハルシネーション） |
| 論理の検査 | 循環、矛盾、証明責任の配分の矛盾 |
| 期待つきのテスト | ルールの変更で結論が変わったこと |
| 別のシステムとの突き合わせ | ルールの意味の誤り |

どれも完全ではありませんが、重ねることで「もっともらしい誤り」の多くを機械で見つけられます。

### 仕組み4: 出力に根拠と前提を必ず添える

結論だけを出さず、次の情報を必ず添えます。

- 結論を導いたルールと、その根拠（条文など）
- 前提にした事実と、その確からしさ（証明済みか、推測か）
- 使ったルールの確認状態（未確認のルールを使ったなら、そう表示する）
- 人の評価に依存した部分
- 扱っていない範囲（適用期間外、未登録のルール）

このリポジトリの評価レポートは、この 5 点を必ず表示します（第26章）。

### 仕組み5: 位置づけを明示する

システムが出すものが「判断」なのか「判断の補助」なのかを、利用規約や画面で明示します。このリポジトリでは、出力を「論点の整理と立証計画の補助」と位置づけ、「法的判断は利用者が行う」ことを毎回表示しています。利用者は弁護士などの専門家、または組織内で自らの業務に使う法務担当者を想定しています。

### 仕組み6: 変更を管理する

ルールの変更は、ファイルの差分としてレビューできる形で管理し（Git など）、誰がいつ何を変えたかを残します。変更のたびにテストを回し、結論が変わった事案を一覧にします。

## 21.3 専門家がいない場合

専門家によるレビューを確保できないプロジェクトもあります（このリポジトリがそうです）。その場合の考え方は次のとおりです。

1. **「専門家が確認済み」という前提でシステムを作らない**
2. 典拠の明記と自動検証で、確認できる部分を最大限に機械化する
3. 未確認であることを、出力のたびに利用者に見せる
4. 利用者自身が確認した結果を記録できるようにし、確認を運用の中で積み上げる
5. 用途を、利用者が自分で判断できる専門家の補助に限る

## 21.4 チェックリスト

- [ ] ルールごとに典拠と確認状態を持っているか
- [ ] LLM が作った内容を、機械で検証してから人が見ているか
- [ ] 出力に、根拠・前提・確認状態・人の評価・扱っていない範囲を添えているか
- [ ] システムの位置づけ（判断か、補助か）を明示しているか
- [ ] ルールの変更履歴と、変更による結論の変化を追えるか
- [ ] レビューが形骸化していないかを、数字で見ているか
- [ ] 業務に関わる法規制を確認したか

## まとめ

- 主なリスクは、もっともらしい誤り、誤りの固定化、検証できない出力、適用範囲の取り違え、レビューの形骸化、責任のあいまいさ、法規制
- 確認状態、典拠の必須化、自動検証の積み重ね、根拠と前提の提示、位置づけの明示、変更管理で抑える
- 専門家がいなければ、確認済みを前提にせず、未確認であることを利用者に見せ続ける
