# 第20章 Claude Code や Codex でできること

Claude Code（Anthropic）や Codex（OpenAI）のような**コーディングエージェント**は、リポジトリのファイルを読み、コマンドを実行し、コードを書き、テストを走らせて結果を見ながら作業を進める AI です。この章では、オントロジーを使うシステムづくりで、こうしたエージェントに何を任せられるかを整理します。具体的な経験は、このリポジトリの開発を振り返る第27章で紹介します。

## 20.1 コーディングエージェントの特徴

チャットで LLM に質問するのとの違いは、**自分で動かして確かめられる**ことです。

| チャットの LLM | コーディングエージェント |
|--------------|---------------------|
| コードを提案する | コードを書いて、実行して、結果を見て直す |
| 説明は文書の知識に基づく | 実際のデータベースやツールで試した結果に基づく |
| 1 回のやりとりで完結 | 調査 → 設計 → 実装 → テスト → 文書化を続けて行う |
| リポジトリの全体は見えない | リポジトリを読み、既存の書き方に合わせる |

オントロジーの分野では、仕様や製品のドキュメントが少なく、**実際に動かさないとわからないこと**が多いので、この「動かして確かめる」力がとくに役立ちます。

## 20.2 任せられること

| 作業 | エージェントが行うこと | 例（このリポジトリ） |
|------|-------------------|-----------------|
| 調査 | 仕様・API・データの形を実際に取得して調べる | e-Gov 法令 API を叩いて、応答の形式（JSON に XML が base64 で入っている）や改正履歴の構造を確認 |
| 環境構築 | Docker、ドライバ、依存関係の準備 | TypeDB を docker compose で起動し、Python ドライバの API を確認 |
| スキーマの設計と検証 | スキーマを書き、実機で定義して確かめる | 提案書の TypeQL を実機で実行し、定義の順序の問題や文書の誤りを発見 |
| データの取り込み | 取り込みスクリプトを書き、元データと突き合わせる | 民法 27 版の取り込み、無作為に選んだ 200 規定の照合 |
| ルールのコード化 | 文書のルールを、決めた形式のデータやコードにする | 条文から規範の YAML を作成（根拠条文の文言を引用） |
| 変換器・生成器 | 宣言的な定義から実行用のコードを生成する仕組み | 規範の YAML から TypeQL 関数を生成するコンパイラ |
| テスト | 期待する答えつきのテストを作り、回し続ける | 44 件の事案テスト、規範の検証テスト |
| 性能の調査 | 計測して原因を切り分け、直す | 関数の呼び方を変えて 8 分半 → 19 秒 |
| 文書化 | 設計判断、制約、結果を文書にまとめる | 提案書・フェーズごとの結果・この教科書 |

## 20.3 任せる上でのコツ

### コツ1: 問いと完了条件を先に渡す

「オントロジーを作って」ではなく、「この問いに答えられるようにして。完了条件は、このテスト事案で期待どおりの結論が出ること」と頼みます。エージェントは完了条件を目標に、試行錯誤を繰り返せます。

### コツ2: 機械で検証できる仕組みを先に作らせる

エージェントの出力を人が全部読むのは大変です。代わりに、**検証の仕組み**（テスト、元データとの照合、引用の照合、循環の検査）を作らせ、それが通ることを確かめます。このリポジトリでは、規範の根拠条文を条文層と自動照合する仕組みを作ってから規範を書いたので、条文番号の誤りや存在しない文言は、作った時点で見つかるようになっています。

### コツ3: 決めるべきことは人が決める

用途、範囲、誰がレビューするか、どこまでを正しいとみなすか、といった判断は、エージェントに任せず人が決めます。エージェントが選択肢と推奨を示し、人が選ぶ形が効率的です。このリポジトリでは、着手前に「用途」「対象分野」「実行環境」「専門家を確保できるか」の 4 点を人が決め、その答え（とくに「専門家を確保できない」）が設計全体に影響しました（第27章）。

### コツ4: 変更を小さく区切り、記録を残す

フェーズごとにコミットし、文書に結果と分かったことを書かせます。後から「なぜこうなっているか」を追えるようにします。

## 20.4 人が担うべきこと

| 人が担うこと | 理由 |
|------------|------|
| 問いと範囲の決定 | 何に使うかは組織が決める |
| 分野の正しさの確認 | エージェントは典拠に基づいて書けるが、正しさの最終確認は専門家の役割 |
| 設計上の大きな判断の承認 | 正本をどこに置くか、何を捨てるか |
| 外部への影響がある操作の承認 | 公開、プッシュ、本番データの変更 |
| 出力の位置づけの決定 | 「判断」を出すのか、「判断の補助」を出すのか |

## 20.5 エージェントとオントロジーの相性

エージェントとオントロジーには、互いを強める関係があります。

- **オントロジーはエージェントの「作業対象」として扱いやすい**: スキーマ・ルール・テストがテキストで書け、機械で検証できる。エージェントは検証が通るまで自分で直せる
- **オントロジーはエージェントの「道具」にもなる**: 第19章のように、エージェントが知識ベースを呼び出して正確な事実と推論を得る
- **宣言的な定義から生成する設計と相性がよい**: ルールを YAML で書き、そこからデータベースの関数を生成する、という構成は、エージェントが定義を書き、生成器と検証が品質を保つ、という分担にしやすい

## まとめ

- コーディングエージェントは、読み・書き・実行・確認を繰り返せるので、ドキュメントが少なく動かさないとわからない分野で役立つ
- 調査、環境構築、スキーマの検証、取り込み、ルールのコード化、生成器、テスト、性能調査、文書化を任せられる
- 問いと完了条件を先に渡し、機械で検証できる仕組みを先に作らせ、判断は人が行う
