# 第6章 名前と意味を共有する

オントロジーのもう一つの大きな役割は、**同じものに同じ名前を付け、同じ意味で使う**ことです。システムや組織をまたいでデータをつなぐとき、ここが土台になります。

## 6.1 データ統合で何が起きているか

ある会社に、次の3つのシステムがあるとします。

| システム | 顧客の表し方 |
|---------|------------|
| 販売管理 | `customer.cust_cd = 'C0012'`、名称「株式会社ABC」 |
| 会計 | `torihikisaki.code = '100345'`、名称「(株)エービーシー」 |
| CRM | `account.id = 'a8f3...'`、名称「ABC Corporation」 |

この3つが同じ会社だとわかるのは、担当者の頭の中だけです。売上と入金と商談を合わせて分析しようとすると、まず「どれとどれが同じか」の対応表を作る作業から始めることになります。

さらに厄介なのは、**同じ言葉が違う意味で使われている**ことです。

- 販売管理の「顧客」は、一度でも注文した会社
- CRM の「顧客」は、商談中の見込み客も含む
- 会計の「取引先」は、仕入先も含む

名寄せ（同じものを同定する）と、意味の定義（何を指すかをそろえる）の両方が必要です。

## 6.2 グローバルな ID

オントロジーの世界、とくに RDF（第11章）では、モノにも概念にも **URI（Web のアドレスと同じ形式の ID）** を付けます。

```
https://example.com/id/company/ABC          ← 会社ABCそのもの
https://example.com/ontology/Customer       ← 「顧客」という概念
```

RDB の主キーは「そのテーブルの中で一意」ですが、URI は「世界中で一意」になるように付けます。各システムのコードは、この URI への対応づけとして持ちます。

```
company/ABC  販売管理のコード  C0012
company/ABC  会計のコード      100345
company/ABC  CRM のID          a8f3...
```

URI でなくてもかまいません。大事なのは、**システムごとの ID とは別に、モノそのものを指す共通の ID を決める**ことです。このリポジトリでは、法令の条文に `129AC0000000089/a95/p3`（民法 95 条 3 項）のような ID を付けています。e-Gov の法令 ID を土台にしているので、他のシステムとも対応づけやすくなっています（第23章）。

## 6.3 概念の定義を共有する

「顧客」の意味を合わせるには、概念に定義を付けて共有します。

```
顧客（Customer）
  定義: 当社と1件以上の受注契約を締結したことがある法人または個人
  サブクラス: 法人顧客、個人顧客
  関連: 見込み客（Prospect）とは別の概念
```

これを各システムの担当者が参照し、自分のシステムのデータがどの概念に当たるかを対応づけます（「CRM の account のうち、受注実績があるものが顧客」）。こうして、システムごとの言葉を、共通の概念に橋渡しできます。

## 6.4 標準の語彙を使う

すべての概念を自分で定義する必要はありません。分野ごとに、広く使われている標準の語彙（オントロジー）があります。

| 語彙 | 分野 | 例 |
|------|------|-----|
| schema.org | Web 全般（組織・人・商品・イベントなど） | `Organization`、`Person`、`Product`、`Offer` |
| Dublin Core | 文書のメタデータ | `title`、`creator`、`date` |
| FOAF | 人と人のつながり | `Person`、`knows` |
| SKOS | 分類体系・用語集 | `Concept`、`broader`（上位概念）、`narrower` |
| PROV-O | データの来歴 | `Entity`、`Activity`、`wasDerivedFrom` |
| 業界標準 | 金融（FIBO）、医療（SNOMED CT）、生命科学（Gene Ontology）など | 第8章 |

標準の語彙を使う利点は、**他社のデータや公開データと最初からつながる**ことです。たとえば Web ページに schema.org の `Product` と `Offer` で商品情報を埋め込んでおけば、検索エンジンがそれを読み取って検索結果に価格を表示できます。

Java でいえば、自前でクラスを作る代わりに、標準ライブラリのインタフェース（`java.time.LocalDate` など）を使うのと同じ発想です。

## 6.5 上位オントロジー

さらに抽象度の高い、分野を問わない基本概念を定義したものを**上位オントロジー**と呼びます。「モノ（物体）」「出来事」「性質」「時間」「場所」といった、どの分野にも出てくる概念です。BFO（Basic Formal Ontology）や DOLCE が知られています。

複数の分野のオントロジーが同じ上位オントロジーの下で作られていれば、分野をまたいだ統合がしやすくなります。ただし、上位オントロジーは抽象的で学習コストが高いので、**最初から使う必要はありません**。業務で使うなら、まず自社の概念をはっきりさせ、必要に応じて業界標準につなぐ、という順番がおすすめです。

## 6.6 意味の違いを書く

統合で一番難しいのは、「似ているが同じではない」概念の扱いです。オントロジーでは、概念どうしの関係を細かく書き分けられます。

| 関係 | 意味 | 例 |
|------|------|-----|
| 同じ | 完全に同じものを指す | 販売管理の「顧客」= 共通概念の「顧客」 |
| より狭い | 一部を指す | CRM の「顧客」は「顧客」と「見込み客」を合わせたもの。共通概念の「顧客」はその一部 |
| 関連する | 同じではないが関係がある | 会計の「取引先」と「顧客」 |

SKOS の `exactMatch`、`broadMatch`、`narrowMatch`、`relatedMatch` は、まさにこの対応関係を書くための語彙です。

## まとめ

- データ統合には、同じものを同定する（名寄せ）ことと、意味の定義をそろえることの両方が要る
- システムごとの ID とは別に、モノそのものを指す共通の ID を決める
- 概念には定義を付けて共有し、可能なら標準の語彙を使う
- 「同じ」「より狭い」「関連する」といった対応関係を書き分ける

| 概念 | RDB | Java | オントロジー |
|------|-----|------|------------|
| ID | テーブル内で一意の主キー | オブジェクトの参照 | 世界で一意の ID（URI など） |
| 意味の定義 | 設計書・テーブルコメント | Javadoc | 概念の定義としてモデルに含める |
| 標準 | （業界の帳票仕様など） | 標準ライブラリ | 標準の語彙・上位オントロジー |
| システム間の対応 | 変換テーブル・ETL | アダプタ | 概念どうしの対応関係（同じ・より狭い など） |
