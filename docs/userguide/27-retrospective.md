# 第27章 AI と進めた開発の振り返り

このリポジトリは、利用者（リポジトリの持ち主）と、コーディングエージェントの Claude Code が対話しながら作りました。この章では、その進め方を振り返り、AI に任せられたこと、人が決めたこと、実際に動かすまでわからなかったことを整理します（第20章の具体例です）。

## 27.1 進め方の流れ

```mermaid
flowchart LR
  P[提案書<br/>調査・方式の比較・設計案] --> D[決定<br/>4 つの論点を人が決める]
  D --> V[実機での検証<br/>提案書の TypeQL を実行]
  V --> P1[フェーズ1<br/>条文層]
  P1 --> P2[フェーズ2<br/>規範層とコンパイラ]
  P2 --> G[この本]
```

| 段階 | 主な成果 | 人の関わり |
|------|---------|----------|
| 提案書 | 日本の法体系と法的推論の調査、5 つの方式の比較、スキーマ案 | 方向性の確認 |
| 決定 | 用途・対象分野・実行環境・専門家の有無 | **4 つの論点に回答** |
| 実機での検証 | TypeDB を起動し、提案書の TypeQL をすべて実行 | 結果の確認 |
| フェーズ1 | 民法の版つき取り込み、参照の抽出 | 「進めてください」 |
| フェーズ2 | 規範 29 件、コンパイラ、事案の評価 | 「進めてください」 |

## 27.2 人が決めたこと

エージェントは、着手前に 4 つの論点を示し、それぞれに推奨を添えて人に尋ねました。

| 論点 | 人の回答 | 設計への影響 |
|------|---------|------------|
| 用途 | 実務家の支援用 | 正確さと根拠の提示が必須になった |
| 対象分野 | 推奨どおり（意思表示・売買・時効） | 規範を数十件に絞れた |
| 実行環境 | docker compose、Python | 再現できる手元の環境 |
| 専門家のレビュー | 確保できない | **設計全体を「確認済みを前提にしない」方向に変えた** |

とくに最後の回答は、エージェントが「実務家向けなのに専門家がいない」という緊張関係を指摘し、典拠の必須化・確認状態・自動照合・出力の注意表示という代替策を設計に組み込むきっかけになりました（第21章）。**用途と責任に関わる判断は人が行い、その判断を設計に落とすのはエージェントが行う**、という分担です。

## 27.3 AI に任せられたこと

| 作業 | 内容 |
|------|------|
| API の調査 | e-Gov 法令 API を実際に呼び、応答の形（JSON の中の base64 の XML）、改正履歴の並び順、同じ施行日に複数の改正がある場合の扱いを確かめた |
| 実機での検証 | 提案書の TypeQL を TypeDB で実行し、例題の結論が期待どおりかをテストにした |
| 取り込み・解析 | XML の解析、版の比較、参照の抽出（附則の「新法」、範囲、括弧書き、章・節への参照など） |
| 規範の作成 | 条文の文言を確認しながら 29 件の規範を YAML で作成。根拠条文の文言を引用し、自動照合を通した |
| 生成器 | 規範から TypeQL 関数を生成するコンパイラ |
| テスト | 単体テスト、44 件の事案テスト、元データとの突き合わせ |
| 性能の改善 | 計測して原因を特定し、取り込みを 434 秒 → 32 秒、評価を 8 分半 → 19 秒に |
| 文書化 | 決定事項、各フェーズの結果、分かった TypeDB の挙動、この本 |

## 27.4 動かすまでわからなかったこと

ドキュメントを読むだけではわからず、実機で動かして初めてわかったことが多くありました。オントロジーの分野は情報が少ないので、「動かして確かめる」ことの価値が大きいと言えます。

### 提案書の誤り

- 提案書の TypeQL は、節ごとに分けて定義すると、節をまたいだ参照のせいで失敗した。すべてを 1 回の定義にまとめる必要があった
- 影響分析のクエリ（Q4）が、参照を逆向きにたどっていた（95 条「が」参照するものではなく、95 条「を」参照するものをたどるべきだった）。条文層を実装して実データで試したときに気づいた

### TypeDB の挙動

| わかったこと | どう気づいたか |
|------------|-------------|
| `or` の分岐の中で否定と比較を組み合わせるとエラー | スキーマの定義が失敗し、関数を 1 つずつ外して原因を特定 |
| IID だけで照合した変数は型が推論されない | 取り込みの高速化で IID を使ったら型エラー。最小の例で再現して確認 |
| 1 つのクエリが失敗すると、同じトランザクションの後続も失敗する | 上の調査中に、無関係なクエリまで同じエラーになったことから |
| 1 クエリの変数は 65,535 個まで | 法令全体を 1 回で入れようとしてエラー |
| 属性の多重度の既定は 0 か 1 | 典拠を複数持つ規範の書き込みが、コミット時に失敗 |
| 引数のない関数を否定の中で呼ぶと遅い | 事案テストが 8 分半かかり、関数ごとに時間を計測 |

### データと規範の問題

- 条文の参照の抽出で、「前項…第一条…同項第一号」の「同項」が正しく解決されない誤りが、テスト用の小さな法令で見つかった
- 評価レポートに、関係のない詐欺・強迫の抗弁が表示された。共通の事実（取消しの意思表示）が原因だとわかり、表示の規則を改めた

いずれも、**テストや元データとの突き合わせ、実際の出力を見ること**で見つかっています。エージェントに任せるときほど、検証の仕組みを先に作ることが大切です（第20章のコツ2）。

## 27.5 うまくいったこと

- **問いと完了条件を先に決めた**: 提案書の段階で「答えたい問い」と、フェーズごとの完了条件を決めていたので、エージェントが自分で到達を判断できた
- **検証の仕組みを先に作った**: 根拠条文の自動照合、元データとの突き合わせ、期待つきの事案テストが、誤りを早く見つけた
- **宣言的な定義から生成した**: 規範は YAML、関数は生成。性能の問題もコンパイラを直すだけで全関数に反映できた
- **分かったことを文書に残した**: 各フェーズの結果に TypeDB の挙動を記録したので、次の作業や、この本に生かせた

## 27.6 課題として残っていること

| 課題 | 内容 |
|------|------|
| 専門家の確認 | 規範はすべて未確認。典拠の頁との照合と、利用者による確認の記録が必要 |
| 旧法の規範 | 改正前の事案を扱えない（フェーズ 3） |
| 根拠の保存 | 推論の結果と根拠をデータとして書き戻す仕組み（実体化）がまだない |
| AI による規範の候補抽出 | 条文から規範の候補を作り、レビューする流れ（フェーズ 4） |
| 利用者向けの入口 | 現在はコマンドラインだけ。LLM から評価をツールとして呼ぶ仕組み（第19章）は未実装 |

## まとめ

- 用途と責任に関わる判断は人が行い、その判断を設計と実装に落とす作業をエージェントが担った
- 調査・実機検証・取り込み・規範の作成・生成器・テスト・性能改善・文書化をエージェントに任せられた
- ドキュメントからわからない挙動や、設計書の誤りの多くは、実際に動かして見つかった
- 問いと完了条件、検証の仕組み、宣言的な定義からの生成、記録を残すことが、AI と進める開発の鍵だった
