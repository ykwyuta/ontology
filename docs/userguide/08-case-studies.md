# 第8章 事例

この章では、オントロジーや知識グラフが実際に使われている分野を紹介します。いずれも公開資料で確認できる範囲の説明にとどめ、出典は[付録C](appendix-c-references.md)にまとめています。数字や採用状況は時期によって変わるので、最新の状況は出典で確認してください。

## 8.1 医療: SNOMED CT

### 何をしているか

SNOMED CT は、病名・症状・処置・検査・薬などの臨床用語を体系化した、世界最大級の医療用語集（オントロジー）です。SNOMED International という非営利団体が管理しています。数十万の概念があり、それぞれに ID と定義、概念どうしの関係（「心筋梗塞」は「心疾患」の一種、部位は「心筋」、など）が付いています。

### オントロジーとしての特徴

- 概念が「is-a」の階層と、「部位」「原因」などの属性関係で定義されている（第2章・第3章）
- 定義は記述論理（OWL の一部。第11章）で書かれていて、推論によって分類の整合性を検査できる
- 電子カルテに病名を ID で記録することで、病院やシステムをまたいで同じ意味で集計できる（第6章）

### ビジネスの観点

英国の NHS など、複数の国で電子カルテの標準用語として採用されています。医療機関・製薬会社・保険者がデータを共有したり、臨床研究のために多数の病院のデータを集めたりするときに、「同じ病名を同じ ID で」記録してあることが前提になります。

**教訓**: 用語の標準化は、1 社ではなく業界全体で取り組むと効果が大きい。その代わり、管理団体と更新の仕組みが必要になる。

## 8.2 生命科学: Gene Ontology

### 何をしているか

Gene Ontology（GO）は、遺伝子や遺伝子産物（タンパク質など）の働きを記述するための語彙です。「分子機能」「生物学的プロセス」「細胞の構成要素」の 3 つの観点で概念が階層化されています。世界中の研究データベースが、遺伝子に GO の概念を注釈（アノテーション）として付けています。

### 使われ方

実験で「この条件で活性が上がった遺伝子 200 個」が得られたとき、それらに共通する GO の概念を調べる（エンリッチメント解析）と、「免疫応答に関わる遺伝子が多い」のような傾向がわかります。階層をたどる推論（「T 細胞の活性化」は「免疫応答」の一種）が分析の中心です（第4章）。

**教訓**: 階層化された共通語彙があると、個別のデータから「上位の意味」を集計できる。

## 8.3 金融: FIBO

### 何をしているか

FIBO（Financial Industry Business Ontology）は、金融取引に出てくる概念（法人、契約、証券、デリバティブ、ローンなど）を定義したオントロジーで、EDM Council が中心になって作り、OWL で公開されています。

### 使われ方

金融機関では、規制当局への報告や、リスク管理のために、社内のさまざまなシステムのデータを同じ定義で集める必要があります。FIBO は、その「共通の定義」の参照先として使われます。たとえば「取引相手（カウンターパーティ）」「親会社・子会社の支配関係」を FIBO の概念に対応づけると、グループ全体での取引相手ごとのリスクの集計がしやすくなります。

- 法人と法人の関係（親子会社、支配）を推移的にたどる（第3章・第4章）
- 社内の用語と FIBO の概念を対応づけ、データ定義の辞書として使う（第6章）

**教訓**: 規制対応のように「定義の正確さ」が問われる分野では、公開された業界標準オントロジーが、社内の議論の出発点になる。

## 8.4 製造: 部品表とデジタルツイン

### 何をしているか

製造業では、製品・部品・設備・工程・不具合の情報が、設計（CAD/PLM）、生産（MES）、保守（CMMS）など別々のシステムにあります。これらをグラフで結び、「この部品のロットを使った製品はどれか」「この不具合はどの工程・設備に関係するか」をたどれるようにする取り組みが広がっています。

### オントロジーとしての特徴

- 部品表は「部品である」という推移的な関係の典型（第4章）
- 設備・センサー・計測値の関係を記述する語彙もある。プラントのライフサイクルデータの国際規格 ISO 15926 や、ビルの設備と計測点を記述する Brick Schema など
- 工程と品質のルール（「この材料はこの温度範囲で加工する」）をモデルに持たせ、逸脱を検出する（第4章のルール）

### ビジネスの観点

品質問題が起きたときの影響範囲の特定（リコール対象の絞り込み）、保守計画、設計変更の影響分析（第7章のパターン4）に効きます。

**教訓**: 部門ごとのシステムを置き換えずに、その上に「つなぐための層」としてグラフを作るのが現実的。

## 8.5 EC・検索: ナレッジグラフと schema.org

### 検索エンジン

Google は 2012 年に「Knowledge Graph」を発表し、「文字列ではなくモノ（things, not strings）」を検索するという考え方を示しました。人物・場所・組織などのモノと、その関係をグラフで管理し、検索結果の横に情報パネルを表示するなどに使っています。

### schema.org

schema.org は、検索エンジン各社（Google、Microsoft、Yahoo!、Yandex）が 2011 年に共同で始めた、Web ページに構造化データを埋め込むための語彙です。商品ページに `Product`、`Offer`、`AggregateRating` を埋め込むと、検索エンジンがそれを読み取り、検索結果に価格や評価を表示できます。**標準語彙を使うと、自社データが外部のサービスとつながる**典型例です（第6章）。

### EC サイトの商品グラフ

大規模な EC サイトでは、商品・カテゴリ・ブランド・属性（色、サイズ、素材）の関係を知識グラフで管理し、検索や推薦に使っています。Amazon は商品知識グラフを自動で構築・拡充する研究（AutoKnow）を発表しています。出品者ごとにバラバラな商品情報を、共通の属性とカテゴリに整理する作業が中心です。

**教訓**: ユーザーが目にする検索・推薦の品質は、裏側の「意味の整理」に支えられている。

## 8.6 公共・法務: 法令データと要件判定

### 法令データの機械可読化

日本では e-Gov 法令検索が、法令を XML（法令標準 XML）で公開し、API（法令 API）で取得できるようにしています。条・項・号の構造や改正の履歴が機械で扱えるようになっています（第23章）。欧州では、法令に共通の ID を付ける ELI（European Legislation Identifier）や、法令文書の XML 標準 Akoma Ntoso（OASIS の LegalDocML）が使われています。

### 法的ルールの記述

法律の「要件 → 効果」の構造を機械可読に書く取り組みとして、OASIS の LegalRuleML や、日本の国立情報学研究所の佐藤健氏らによる PROLEG（要件事実論を論理プログラムで表したシステム）があります。PROLEG は、民事訴訟の「請求原因・抗弁・再抗弁」の構造を、原則と例外のルールとして表します（第14章、第24章）。

### 行政サービスでの要件判定

補助金・給付・許認可の「受けられるかどうか」の判定ルールを機械可読にして、申請前に自己診断できるようにしたり、窓口の判定を揃えたりする取り組みも各国で行われています。ルールの改正が頻繁で、根拠となる条文の説明が求められる点が、ルール判定と説明（第7章のパターン3）の典型です。

**教訓**: 法令のように「根拠を示すこと」が必須の分野では、結論だけを出す仕組みより、ルールとその根拠条文をつないで持つ仕組みのほうが受け入れられやすい。このリポジトリもこの考え方で作っています（第5部）。

## 8.7 事例から見える共通点

| 共通点 | 内容 |
|-------|------|
| 範囲を絞って始めている | 医療なら臨床用語、金融なら規制報告など、目的のはっきりした範囲から |
| 共通 ID と定義が土台 | どの事例も「同じものを同じ ID で」が出発点 |
| 管理する組織がある | 標準化団体、社内のデータ管理部門など、モデルを更新し続ける担い手がいる |
| 既存システムは置き換えない | 既存のデータベースの上に、つなぐ層・意味の層として作る |
| 推論は「階層」と「関係をたどる」が中心 | 複雑な論理推論より、階層の集約と経路の探索が実務の主役 |

## まとめ

- 医療（SNOMED CT）、生命科学（Gene Ontology）、金融（FIBO）、製造（部品表・設備）、EC・検索（ナレッジグラフ・schema.org）、公共・法務（法令データ・ルール記述）で使われている
- どの事例も、範囲を絞り、共通の ID と定義を土台にし、管理する担い手を置いている
- 既存のシステムを置き換えるのではなく、その上に意味の層を重ねている
