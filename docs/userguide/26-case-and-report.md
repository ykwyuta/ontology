# 第26章 事案層と評価レポート

事案層は、個別の事案（誰が誰に何を請求し、どんな事実がどこまで証明されているか）を持つ層です。この章では、事案の入力と、評価レポートの出力を見ます。

## 26.1 推論の単位は「訴訟物」

提案書では、事案を「売買契約」「意思表示」「当事者」のグラフで表す計画でした。実装では、推論の単位を**訴訟物（請求）**にそろえ、事実と時点はすべて訴訟物に結びつけました。

```typeql
entity claim,                              # 訴訟物
  owns claim-id @key, owns claim-type,
  plays claim-party:claim, plays fact-finding:subject, plays time-point:subject, ...;
relation claim-party, relates claim, relates claimant, relates respondent;
relation fact-finding, relates subject, owns fact-code, owns proof-status;   # 事実と証明状態
relation time-point, relates subject, owns anchor-code, owns at;             # 判定の時点
```

要件事実論は訴訟物ごとに組み立てるので、この単位が自然です。また、すべての関数が「訴訟物を受けて訴訟物を返す」同じ形になり、機械的に生成できます（第25章）。その代わり、事実の説明は「請求する側」「請求される側」を主語にして書いています（第3章のロール）。

## 26.2 事案を YAML で入力する

例題（第22章）の入力は次のとおりです。

```yaml
case-id: demo-001
description: 絵画の売買代金請求に対する錯誤取消しの抗弁
claims:
  - id: demo-001-price
    type: sale-price                    # 売買代金支払請求
    claimant: X
    respondent: Y
    time-points:                        # 新旧の規定を判定する時点
      declaration: 2024-05-10
      contract: 2024-05-10
      claim-arose: 2024-05-10
    facts:                              # 要件事実と証明状態
      N555.contract-concluded: admitted                       # 売買契約（自白）
      N95-1-2.mistake-in-motive: proven                       # 基礎事情の錯誤
      N95-2.motive-indicated: proven                          # その表示
      N95-1.material: proven                                  # 重要な錯誤
      N123.cancellation-declared: admitted                    # 取消しの意思表示
      N95-3.gross-negligence: proven                          # Y の重大な過失
      N95-3-1.counterparty-knew-or-gross-negligence: unclear  # X の悪意・重過失は真偽不明
    expect: granted                     # テスト用の期待
```

証明状態は「自白」「証明済」「真偽不明」「否定」の 4 つで、入力のない事実は「主張なし」として扱います（第5章）。

## 26.3 評価レポート

`legal-onto evaluate cases/demo-001.yaml` の出力（抜粋）です。

```
■ 訴訟物 demo-001-price（sale-price）: X → Y
  結論: 請求を認める

  論証（事実が入力された規範のみ表示）:
    [成立] G555-price 売買代金支払請求（請求原因・立証責任: 請求する側）
        ✓ 請求する側と請求される側が、目的物を代金額を定めて売買する契約を締結したこと［自白］
      [要件充足・例外により不成立] D95 錯誤による取消し（抗弁・立証責任: 請求される側）
          ✓ 〔NR95 錯誤による取消権の発生〕が成立すること
          ✓ 請求される側が、…取り消す旨の意思表示をしたこと［自白］
        [成立] R95-3 表意者の重大な過失（再抗弁・立証責任: 請求する側）
            ✓ 錯誤が、請求される側（表意者）の重大な過失によるものであったこと［証明済、規範的要件］
          [不成立] E95-3 相手方の悪意・重過失又は共通錯誤（再々抗弁・立証責任: 請求される側）
              次のいずれか:
                ? 請求する側が、錯誤を知り、又は重大な過失によって知らなかったこと［真偽不明］
                - 請求する側が、請求される側と同一の錯誤に陥っていたこと［主張なし］

  結論を変えうる立証:
    - 請求される側: 請求する側が、錯誤を知り、又は重大な過失によって知らなかったこと［真偽不明］
    - 請求される側: 請求する側が、請求される側と同一の錯誤に陥っていたこと［主張なし］

  注意:
    ! 専門家の確認を経ていない規範を使っている: G555-price、D95、NR95、R95-3（unreviewed）
    ! 利用者の評価に依存する規範的要件: …重要なものであること、…重大な過失によるものであったこと

この結果は、登録した規範と入力した事実の証明状態から機械的に導いたもので、…法的判断は利用者が行うこと。
```

読み方:

- Y の錯誤取消し（抗弁）は要件を満たしているが、Y に重大な過失がある（再抗弁）ので取り消せない
- X が Y の錯誤を知っていた（再々抗弁）ことは真偽不明なので、証明責任を負う Y に不利に扱われる
- よって請求は認められる
- **結論を変えるには、Y が「X が錯誤を知っていた（または重過失で知らなかった）」こと、または「X も同じ錯誤に陥っていた」ことを立証すればよい**

最後の点が、第22章の問い「不足事実」への答えです。

## 26.4 レポートの設計で工夫したこと

### 結論だけでなく、論証の木を出す

第21章の「出力に根拠と前提を添える」に従い、どの規範が成立し、どの事実がどの状態だったかを、層の構造のまま表示します。

### 争点になっている規範だけを表示する

29 の規範をすべて表示すると読めません。そこで、**その規範に固有の事実が 1 つでも入力されている規範**だけを表示します。最初は「事実が 1 つでも入力されていれば表示」にしていましたが、「取消しの意思表示」のように錯誤・詐欺・強迫に共通する事実があると、関係のない詐欺や強迫の抗弁まで表示されてしまいました。実際の出力を見て、この規則に改めました。

### 「結論を変えうる立証」を絞る

例外として働く規範は、その対象の規範の要件が満たされているときだけ結論に影響します。たとえば錯誤取消しの要件が満たされていなければ、重過失の再抗弁の事実をいくら立証しても結論は変わりません。そこで、対象の規範の要件が満たされている規範についてだけ、不足している事実を表示します。

### 注意を必ず出す

| 注意 | 出す条件 |
|------|---------|
| 時点が未入力 | 適用期間のある規範が争点なのに、判定の時点がない |
| 適用期間外 | 改正前の事案で、改正後の規範しか登録されていない |
| 未確認の規範 | 結論に関わった規範の確認状態が unreviewed または disputed |
| 規範的要件 | 人の評価に依存する要件を、成立したものとして使った |

## 26.5 テスト

`tests/cases/*.yaml` には 44 件の訴訟物があり、それぞれに期待する結論（`expect`）が書いてあります。規範ごとに、次のパターンを用意しました（第9章「期待する答えを先に書く」）。

- 全要件が証明済み → 規範が成立
- 一部が真偽不明・否定 → 不成立
- 例外が成立 → 不成立
- 例外の例外が成立 → 成立
- 改正前の時点、時点が未入力 → 適用しない
- 抗弁の組み合わせ（弁済と同時履行、錯誤の不成立と詐欺の成立）

規範やコンパイラを変更したら、`pytest` で全件の結論が変わっていないかを確かめます。

## まとめ

- 事案は訴訟物ごとに、事実の証明状態と判定の時点を入力する
- レポートは、結論・論証の木・結論を変えうる立証・注意・位置づけの表示からなる
- 表示する規範と不足事実を絞り込み、実務家が読める量にした
- 期待つきの事案テストで、規範とコンパイラの変更を検証する
