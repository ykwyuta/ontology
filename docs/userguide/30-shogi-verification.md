# 第30章 将棋の審判を検証する・振り返る

この章では、作った審判の正しさをどう確かめたか、実際に動かして分かったこと、民法の試みと比べて見えたことをまとめます。

## 30.1 基準のライブラリと突き合わせる

将棋の大きな利点は、**正解を機械的に得られる**ことです。広く使われている Python の将棋ライブラリ python-shogi を「基準」にして、TypeDB の審判と結果を比べました。

> python-shogi のライセンスは GPL-3.0 です。テストと正解データの作成にだけ使い、審判の実行時には使っていません。

### 全合法手の一致

基準のライブラリで対局をランダムに進めて局面を集め、各局面の**全合法手の集合**が一致するかを比べました。王手への対応・ピン・打ち歩詰めの判定を多く通すために、半分を王手のかかった局面にした回もあります。

| 実行 | 局面 | 王手のかかった局面 | 持ち駒のある局面 | 合法手の総数 | 一致 |
|------|----:|----:|----:|----:|----:|
| 1 回目 | 30 | 1 | 27 | 1,436 | 30/30 |
| 2 回目（半分を王手の局面に） | 80 | 41 | 72 | 2,083 | 80/80 |

### perft

perft は、ある局面から N 手先までの合法手の数を数えたもので、手の生成が正しいかの標準的な検査です。初期局面の perft(1) = 30、perft(2) = 900 が、正しい値と一致しました。

### ルールごとのテスト

ルール ID ごとに、反則になる指し手とならない指し手を用意しました。とくに**境界の例**を重視しました。

| 境界の例 | 期待 |
|---------|------|
| と金のある筋に歩を打つ | 合法（と金は二歩に数えない） |
| 歩を打って王手だが、玉に逃げ道がある | 合法（打ち歩詰めではない） |
| 盤上の歩を進めて（成って）詰ませる | 合法（突き歩詰めは反則ではない） |
| ピンされた金を、同じ筋の中で動かす | 合法 |
| ピンされた金を、筋の外に動かす | 反則（王手放置） |

テストでは、**期待そのものを先に基準のライブラリで確かめて**から、TypeDB の判定と比べています。テストを書く人（今回は AI）が期待を間違えていても、その時点で気づけます。

| テスト | 件数 |
|-------|----:|
| SFEN・USI の解析（TypeDB 不要） | 4 |
| ルールごとの判定・詰み・判定結果の形 | 28 |
| 対局の審判（strict / retry、詰み、千日手、連続王手の千日手、最大手数、投了） | 8 |

## 30.2 実際に動かして分かったこと

民法のときと同じく、TypeDB の挙動にはドキュメントからは分からないものがありました。

| 分かったこと | どう対応したか |
|------------|-------------|
| 整数を返す関数の中で `or` を使い、分岐ごとに戻り値を代入するとエラー（CEX7・CEX18） | 盤をマスのエンティティにし、関数は概念（マス）を返す形にした（第28章） |
| 属性の変数を整数の引数に渡すとエラー（REP35） | マスのエンティティを渡す |
| 引数や束縛済みの変数に `let $x in 関数(...)` で受け直すとエラー（REP21） | 新しい変数で受けて `$y is $x;` で比べる |
| `or` の分岐の中の否定 | 否定を別の関数に分ける（民法と同じ） |
| 概念の組を返す関数（`-> { square, square, piece-type }`） | 問題なく使えた |

Python 側でも、テストのフォルダ名を `tests/shogi` にしたら、基準のライブラリのパッケージ名 `shogi` を隠してしまい、テストが全滅するという問題がありました。

試作の段階でも、期待値の誤りがありました。「飛車の利き」の期待を 8 マスと書いていましたが、実際には利きに自分の駒のマスを含める設計なので 9 マスが正しく、間違っていたのはテストの期待のほうでした。**動かして、結果と期待のどちらが正しいかを考える**ことの大切さは、民法のときと同じです。

## 30.3 性能

| 処理 | 時間 |
|------|------|
| データベースの作成（スキーマ・盤・ルール） | 約 1.6 秒 |
| 初期局面の全合法手（30 手） | 約 1.8 秒 |
| ランダムな局面の全合法手 | 1 局面あたり 約 4〜8 秒 |
| perft(2)（30 局面、計 900 手） | 約 96 秒 |

専用の将棋ライブラリはこの何千倍も速いので、TypeDB の審判は**探索（強さ）には使えません**。用途は「AI が提案した指し手 1 つを判定し、理由を返す」ことに絞っています。それでも 1 手あたり数秒は、AI 対局の審判としては使えるが、評価で大量の局面を扱うには遅い、という状態です。

ここに、オントロジーで表すことの代償がはっきり出ています。

| 得たもの | 払ったもの |
|---------|----------|
| ルールがデータとして読め、ルール ID で集計・説明できる | 速さ |
| ルールの変種（盤の大きさ・駒の違い）にデータで対応できる | 書き方の制約（TypeDB の関数の制約） |
| 反則の理由を、どのマスのどの駒かまで返せる | 実装の手間 |

速さが必要な部分（全合法手の生成）は専用ライブラリに任せ、TypeDB は理由の特定と記録に使う、という分担も考えられます。どちらがよいかは用途次第で、ここでも「目的から選ぶ」（第16章）ことになります。

## 30.4 民法の試みとの比較

| 観点 | 民法 | 将棋 |
|------|------|------|
| ルールの正本 | YAML（規範）→ 関数を生成 | データ（駒の動き・盤）＋ 手書きの関数 |
| 原則と例外 | 請求原因 − 抗弁 ＋ 再抗弁 … | 疑似合法手 − 禁じ手 |
| 推論の中心 | 層化否定（証明できなければ不成立） | 再帰（飛び駒）、仮想の盤、否定（逃げる手がない） |
| 正しさの確認 | 根拠条文の文言の自動照合まで。中身は専門家の確認が必要 | 基準のライブラリと全合法手で突き合わせ |
| 説明 | 論証の木、不足事実、証明責任 | 反則のルール ID と、具体的な理由 |
| 性能の山場 | 引数のない関数を否定の中で呼ぶ（8 分半 → 19 秒） | 指した後の局面の書き込み（仮想の盤で解消） |

2 つの試みに共通していたのは、次の点です。

- **ルールをデータと関数で持ち、ルールごとに ID を付ける**: 判定の理由、集計、根拠の提示がすべて ID を軸にできる
- **「原則から例外を除く」構造**: 法律でも将棋でも、否定を使った層の構造になる
- **検証の仕組みを先に作る**: 民法では根拠条文の照合と事案テスト、将棋では基準のライブラリとの突き合わせ
- **実機で動かして初めて分かることが多い**: TypeDB の制約、性能の問題、設計書や期待値の誤り

違いは、**正解が機械的に得られるかどうか**でした。将棋のように正解が得られる分野では、オントロジーの判定の正しさを高い水準で保証できます。法律のように得られない分野では、典拠・確認状態・出力の注意表示で信頼性を補う必要があります（第21章）。

## 30.5 これからの課題

| 課題 | 内容 |

## まとめ

- 基準のライブラリと突き合わせ、110 局面の全合法手（3,519 手）と perft(2) = 900 が一致した
- テストの期待は、先に基準のライブラリで確かめた
- TypeDB の制約（値を返す関数の `or`、受け直しの REP21 など）は、実際に動かして見つかった
- 速さと引き換えに、ルールの読みやすさ・説明・変種への対応を得た
- 民法と将棋の違いは「正解が機械的に得られるか」で、それが検証と信頼性の作り方を決める
