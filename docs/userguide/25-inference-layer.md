# 第25章 推論層: ルールを関数に変換する

推論層は、規範層の YAML から TypeDB の関数を自動生成する層です。この章では、コンパイラ（`src/legal_onto/compiler.py`）が何を生成するか、なぜその形にしたかを見ます。

## 25.1 規範 1 つにつき 2 つの関数

コンパイラは、規範 N ごとに 2 つの関数を生成します。どちらも訴訟物（請求）`$c` を受け取り、条件を満たせば `$c` を返します。

| 関数 | 意味 |
|------|------|
| `c_N($c)` | N の**要件を満たす**（要件の木と、適用期間の条件） |
| `h_N($c)` | N が**成立する**（要件を満たし、N に対する例外がどれも成立しない） |

第24章の錯誤の再抗弁（R95-3）からは、次の関数が生成されます。

```typeql
# R95-3 表意者の重大な過失（要件）
fun c_r95_3($c: claim) -> { claim }:
match
  $c isa claim;
  $tp isa time-point, links (subject: $c), has anchor-code "declaration", has at $t; $t >= 2020-04-01;
  $f1 isa fact-finding, links (subject: $c), has fact-code "N95-3.gross-negligence"; let $f1 in established();
return { $c };

# R95-3 表意者の重大な過失（成立）層2
fun h_r95_3($c: claim) -> { claim }:
match
  let $y in c_r95_3($c);
  not { let $z0 in h_e95_3($c); };      # 例外（E95-3）が成立しなければ
return { $c };
```

要件の木は、次のように変換します。

| YAML | TypeQL |
|------|--------|
| `fact: X` | `$f isa fact-finding, links (subject: $c), has fact-code "X"; let $f in established();` |
| `all: [...]` | パターンを並べる（かつ） |
| `any: [...]` | `{ … } or { … };`（または） |
| `norm: N` | `let $r in h_n($c);`（他の規範の成立） |
| `valid-from` と `time-anchor` | 事案の時点との比較 |

`established()` は、証明状態が「自白」か「証明済」の事実を返す関数です。真偽不明・否定・未入力の事実は返さないので、**「証明できなければ、なかったことになる」**（第24章の証明責任）が自然に表されます。

## 25.2 結論の関数

規範ごとの関数の上に、結論を出す関数を生成します。

| 関数 | 意味 |
|------|------|
| `ground_holds($c)` | 請求原因が成立し、消滅・障害の抗弁が成立しない |
| `blocked($c)` | 阻止の抗弁（同時履行の抗弁）が成立する |
| `claim_granted($c)` | 請求を認める |
| `claim_granted_in_exchange($c)` | 引換給付で請求を認める |

同時履行の抗弁は、成立しても請求が棄却されるのではなく「代金と引換えに目的物を引き渡せ」という判決になります。そこで、他の抗弁とは別に扱っています。

## 25.3 層化否定が守られる理由

`h_N` は、否定の中で `h_E`（N の例外）だけを呼びます。例外は必ず 1 つ深い層にあるので、否定の中で呼ぶのは常に「より深い層」です。規範を読み込むときに循環がないことを検査しているので（第24章）、生成した関数は必ず層化されています（第5章）。

もし誰かが循環する規範を書いたら、TypeDB に入る前に Python の検証で止まり、どの規範がどう循環しているかが表示されます。

## 25.4 性能のために変えた設計

提案書の段階では、関数を引数のない形で設計していました。

```typeql
# 当初の設計（提案書 4.4）
fun mistake_rebuttal() -> { declaration-of-intent }:
match
  ...
  not { let $d in mistake_rerebuttal(); };
return { $d };
```

この形で 44 件のテスト事案を評価すると、**8 分半**かかりました。計測して原因を切り分けたところ、引数のない関数を否定の中で呼ぶたびに、全事案について評価し直していることがわかりました。件数 × 否定の数に比例して遅くなります。

訴訟物を引数で渡す形（`fun h_x($c: claim)`）に変えると、否定の中では「その事案についてだけ」評価すればよくなり、**19 秒**になりました。生成器（コンパイラ）を直すだけで、すべての関数が一度に直ったのも、ルールから関数を生成する構成の利点です。

## 25.5 TypeDB の制約への対応

実機で動かして見つかった TypeDB 3.13 の制約と、コンパイラでの対応です。

| 制約 | 対応 |
|------|------|
| 同じ変数名を複数の `not` で使うとエラー（REP44） | 否定ごとに `$z0`、`$z1` … と別の名前を付ける |
| `or` の分岐の中で、否定と比較を組み合わせられない | 否定を含む条件を別の関数に分ける（条文層の `reference_active`） |
| `or` のない単独の `{ … }` は構文エラー | 分岐が 1 つなら波括弧を付けない |
| 関数の引数（値）を `has fact-code $x` に直接使うとエラー（REP35） | 属性を別の変数で受けて `==` で比べる |

こうした制約はドキュメントに明記されていないものもあり、実際に定義・実行してみて初めてわかりました。コンパイラに対応を入れておけば、規範を書く人が意識する必要はありません。

## 25.6 再コンパイル

規範を変更したら、`legal-onto load-norms` で読み込み直します。コンパイラは、前回定義した関数の一覧（`compiled-function` として保存）を使って古い関数を削除（`undefine`）し、新しい関数を定義します。生成される TypeQL は `legal-onto compile` で確認できます。

## まとめ

- 規範ごとに「要件を満たす」関数と「成立する」関数を生成し、その上に結論の関数を作る
- 例外は否定で表し、読み込み時の循環検査によって層化否定が保証される
- 引数のない関数から、訴訟物を引数にとる関数に変えて、8 分半が 19 秒になった
- TypeDB の制約への対応はコンパイラに閉じ込め、規範を書く人には見せない
